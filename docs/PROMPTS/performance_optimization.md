# 性能优化任务提示词

## 背景

项目已建立性能基线（见 `docs/PERFORMANCE_BASELINE.md`），当前：
- Bundle 大小：taskpane JS 222.12 KB，dist 总计 491.83 KiB
- 测试运行：258 项，4.32 秒
- 构建正常，测试通过

现在需要进入"分析 → 优化"闭环，改善用户体验。

---

## 任务目标

**分三个阶段，依次进行：**

### 阶段 1：Bundle 大小分析（预计 1 小时）

**目标：** 识别大型依赖，评估优化空间

**任务清单：**
1. 使用 `vite-plugin-visualizer` 或 `rollup-plugin-visualizer` 生成 bundle 可视化报告
2. 分析依赖占比，识别前 5 大模块（预期 Office.js、React 等会占大头）
3. 检查是否有：
   - 未使用的大型依赖
   - 可以按需引入而非全量引入的库
   - 可以懒加载的模块（如计划编辑器对话框）
4. 评估代码分割（code splitting）的收益
5. 输出分析报告：`docs/BUNDLE_SIZE_ANALYSIS.md`

**产出：**
- Bundle 可视化报告（HTML 文件）
- 分析文档，包含：
  - 依赖占比表格
  - 优化建议（按优先级排序）
  - 预期收益评估（KB 级别）
  - 是否值得优化的决策建议

**注意事项：**
- Office.js 是外部依赖，不打包进 bundle，不计入优化范围
- 不要为了优化而优化，收益 < 10KB 的优化不值得做
- 考虑维护成本：懒加载会增加代码复杂度

---

### 阶段 2：渲染性能分析（预计 2 小时）

**目标：** 找出渲染瓶颈，定位优化点

**任务清单：**
1. 使用 React DevTools Profiler 分析关键场景：
   - 打开插件（初始渲染）
   - 发送消息（对话列表更新）
   - 切换工作表（范围选择器更新）
   - 打开"我的工具"（工具列表渲染）
   - 打开计划编辑器（大型对话框渲染）
2. 识别性能瓶颈：
   - 哪些组件渲染时间 > 16ms（60fps 阈值）
   - 哪些组件频繁重渲染（> 5 次/秒）
   - 是否有大列表未虚拟化
   - 是否有昂贵计算未 memo
3. 检查既有优化是否生效：
   - `useMemo` / `useCallback` 是否正确设置依赖
   - `React.memo` 是否正确使用
   - 是否有不必要的上下文传递导致全树重渲染
4. 输出分析报告：`docs/RENDER_PERFORMANCE_ANALYSIS.md`

**产出：**
- Profiler 截图（关键场景的火焰图）
- 分析文档，包含：
  - 瓶颈组件列表（按渲染时间排序）
  - 频繁重渲染组件列表
  - 优化建议（按优先级排序）
  - 预期收益评估（ms 级别）

**注意事项：**
- 在生产构建（`npm run build`）下测试，开发模式性能不准
- 关注用户实际操作路径，不要优化用户不常用的场景
- 60fps = 16ms/frame，< 16ms 的渲染不需要优化

---

### 阶段 3：应用优化（预计 3 小时）

**前置条件：** 完成阶段 1 和阶段 2，基于分析结果决定优化方向

**目标：** 针对性优化，验证效果

**任务清单：**
1. 根据阶段 2 的分析结果，选择 ROI 最高的 3-5 个优化点
2. 逐个优化并验证：
   - 添加 `useMemo` / `useCallback` / `React.memo`
   - 虚拟化大列表（如果有）
   - 拆分大组件（如果有）
   - 懒加载非关键路径模块（如果阶段 1 建议）
3. 每个优化后：
   - 重新运行 Profiler，确认渲染时间改善
   - 运行测试套件，确保功能未破坏
   - 记录前后对比数据
4. 更新性能基线：`docs/PERFORMANCE_BASELINE.md`
5. 输出优化报告：`docs/PERFORMANCE_OPTIMIZATION_REPORT.md`

**产出：**
- 优化代码提交
- 优化报告，包含：
  - 优化清单（每项优化的前后对比）
  - 整体改善（bundle 大小、渲染时间）
  - 测试结果（确保无破坏）
  - 未来优化建议（如果有）

**注意事项：**
- 每次优化后立即测试，不要批量优化后再测试
- 如果优化后性能没有改善，回滚并记录原因
- 不要过度优化：useMemo/useCallback 本身也有成本
- 优先优化用户感知明显的场景（首屏加载、交互响应）

## 执行建议

**推荐顺序：**
1. 先做阶段 2（渲染性能分析），因为用户痛点通常是"操作卡顿"而非"加载慢"
2. 再做阶段 1（Bundle 分析），如果阶段 2 发现没有明显瓶颈
3. 根据阶段 1/2 的分析结果决定是否做阶段 3

**如果时间有限：**
- 只做阶段 2，输出分析报告即可
- 阶段 3 可以按需分多次进行，每次优化 1-2 个点

**如果用户有明确反馈：**
- "加载慢" → 优先阶段 1（Bundle 分析）
- "操作卡顿" → 优先阶段 2（渲染分析）
- "没感觉有问题" → 不需要优化，观察即可

## 注意事项

1. **不要过度工程化：** 如果用户没有明显痛点，性能优化的优先级低于功能开发
2. **测量优先：** 先测量再优化，不要凭感觉优化
3. **用户感知优先：** 优化用户实际操作路径，不要优化边缘场景
4. **保持测试通过：** 每次优化后立即运行测试
5. **记录决策：** 如果分析后决定不优化，也要记录原因
