# 工作日志 2026-08-23

## 主题：AI 辅助计划编辑功能实现

### 背景

用户希望在计划编辑器中加入 AI 辅助功能，通过自然语言描述修改需求，AI 返回修改后的完整计划 JSON，同时保留手动编辑的能力。

### 需求确认

**用户最初提议：** 用户描述修改 → AI 给出脚本 → 用户复制

**最终方案：** 两栏布局
- 左侧：AI 对话界面，自然语言交互
- 右侧：JSON 编辑器，保留手动编辑权利
- 每条 AI 回复提供「应用到编辑器」按钮

用户明确表示：**"应该是两栏的，我感觉那样会方便些，可以保留用户自己修改的权利吧"**

### P1: 服务端 API 实现（1.5h）

**新增文件：** `server/app/plan_chat.py`

**核心函数：**
```python
async def chat_modify_plan(
    current_plan: AnalysisPlan,
    user_message: str,
    connection: ModelConnection,
    timeout: float,
) -> tuple[str, AnalysisPlan]:
    """AI 辅助修改计划。
    
    Args:
        current_plan: 当前的计划 JSON
        user_message: 用户的修改需求描述
        connection: 模型连接配置
        timeout: 超时时间（秒）
    
    Returns:
        (AI 回复文本, 修改后的完整计划)
    """
```

**系统提示词设计：**
- 角色定位：Excel Bro 计划编辑助手
- 提供计划结构说明（steps、acceptanceCriteria、sourceFingerprint、liveness）
- 列举常见操作类型（filter、sort、group、pivot、compute、take、select）
- 要求返回修改说明 + 完整计划 JSON

**Function Calling 格式：**
```python
tools=[{
    "type": "function",
    "function": {
        "name": "return_modified_plan",
        "description": "返回修改说明和完整的修改后计划",
        "parameters": {
            "type": "object",
            "properties": {
                "explanation": {"type": "string"},
                "modifiedPlan": {"type": "object"}
            },
            "required": ["explanation", "modifiedPlan"]
        }
    }
}]
```

**安全处理：**
1. AI 返回的 `acceptanceCriteria` 会被删除（由服务端重算）
2. 保留原有的 `sourceFingerprint`（不让 AI 修改）
3. 通过 `AnalysisPlan.model_validate()` 校验合法性

**新增 API 端点：** `POST /api/plans/chat-modify`

**修改文件：** `server/app/main.py`
- 导入 `chat_modify_plan`
- 导入 `BaseModel`（用于请求/响应模型）
- 导入 `model_timeout_seconds`
- 定义 `PlanChatRequest` 和 `PlanChatResponse`
- 实现端点逻辑，复用现有的错误处理机制（`_map_turn_error`）

## 技术亮点

1. **完整 JSON 输出，避免 diff 合并**
   - AI 返回完整计划而非增量修改
   - 避免了 patch/merge 逻辑的复杂性和错误风险

2. **保留手动编辑能力**
   - 用户可以在应用 AI 计划后继续手动编辑
   - 手动编辑后可以继续与 AI 对话（基于当前编辑器内容）

3. **多轮对话支持**
   - 每次 AI 调用都基于当前编辑器的 JSON
   - 可以连续多次修改，逐步完善计划

4. **应用前可预览**
   - AI 回复显示修改说明（2-3 句话）
   - 用户可以决定是否应用，而非强制覆盖

5. **复用现有校验**
   - 保存时仍经过本地 `assertEditablePlan` + 服务端 `validatePlan`
   - AI 生成的计划必须通过相同的校验规则

6. **安全防护**
   - 删除 AI 生成的 `acceptanceCriteria`（服务端重算）
   - 保留原有的 `sourceFingerprint`（不让 AI 擅自修改）
   - 通过 Pydantic 校验确保返回的计划合法

## 架构决策

### 为什么返回完整 JSON 而非 diff？

**理由：**
1. 简化前端逻辑，避免复杂的 JSON merge 算法
2. 避免 diff 格式解析错误导致的数据损坏
3. AI 生成完整 JSON 更可靠（避免局部修改导致结构不一致）
4. 用户可以完全掌控最终内容（先预览说明，再决定是否应用）

**代价：**
- 每次 AI 调用需要生成完整计划（token 消耗略高）
- 但考虑到计划 JSON 通常不大（< 2KB），这个代价可接受

### 为什么不实时更新右侧 JSON？

**理由：**
1. 保留用户的修改权利（用户可能不想应用 AI 的建议）
2. 避免 AI 错误时直接破坏用户的工作
3. 用户可以对比 AI 建议和当前内容，做出更好的决策

**替代方案：**
- 未来可以增加「实时预览」模式（diff 高亮）
- 但默认仍应保持「手动应用」的控制权
