# 双宿主改造方案(v2.1,二次评审修订)

> 日期:2026-09-26
> 范围:apps/excel-addin、apps/wps-addin、server/app、config/capabilities.json
> v1 性质是架构草案;v2 按评审意见补齐验收用例、能力矩阵、状态迁移与回退关卡
> **验收标准:两个平台呈现相同、安全且可恢复的行为。代码复用只是手段**
> v2.1 明确参数化列映射、可通过的基线关卡、确认绑定与现有 Office 协议兼容性。

## 0. 结论先行

v1 的方向(抽 `packages/core`)成立,但有两处判断错误,已核实并更正:

1. **服务端不是宿主无关的** —— 恢复链路是 Office 专属,WPS 在协议层就进不去
2. **空串比对的风险方向我写反了** —— 是误判写入成功,不是误判未写入。危险等级更高

这两处都不是表述问题,是结论错误。v1 里"服务端是当前架构最健康的部分,建议保持"
这句应当作废。

### 1.1 我的技术判断更正(评审第 5 点)

v1 第 4 节写:读取侧若改用折叠语义,"合法的空串写入会被验收判成未写入"。**这是错的。**

核实 `wpsPlanExecutor.ts:147-149`:

```ts
function matricesEqual(actual: CellValue[][], expected: CellValue[][]): boolean {
  return JSON.stringify(canonicalMatrix(actual)) === JSON.stringify(canonicalMatrix(expected));
}
```

`canonicalMatrix` 对**两侧都**折叠(`canonicalCell:110-115`,`"" → null`)。
所以计划要写 `""`、实际落成 `null`(或反之)时,两边归一后都是 `null`,比对**通过**。

真实风险是**误判写入成功**:回读核对(`:397`)本该是最后一道防线,却对
空串/空值这一类差异失明。比"误判未写入"危险 —— 后者会报错让人看见,前者静默放过。

修正方向是把用途分开:用于旧撤销记录的指纹可沿用旧折叠算法;
"回读是否符合计划"不能再调用同一个折叠比较器,至少必须识别
`expected=""`、`actual=null` 的差异。宿主若无法稳定保留并读回空串,
不得将该写入报告为已严格验证;应在预检拒绝,或明确标为未独立验证。
v1 把指纹兼容性与写后验收混为一谈了。

## 2. 三套身份与恢复语义(评审第 1 点)

### 2.1 核实结果

服务端恢复链路带硬编码的 Office 语义:

```python
# server/app/models.py:2020-2025
@field_validator("workbookIdentity")
def validate_workbook_identity(cls, value: str) -> str:
    if not value.startswith("url:"):
        raise ValueError("未保存或无法稳定识别的工作簿不能启用自动断点续跑")
    return value
```

WPS 的身份是本地磁盘路径,校验规则是 `^[A-Za-z]:\\[^\r\n]+\.xlsx$`
(`wpsPlanExecutor.ts:161-164`)。**它在协议层就被 `url:` 前缀拒绝,
根本进不了 `/api/office/...` 系列接口。**

`_validate_office_recovery_plan`(`main.py:1126-1152`)进一步绑定 Office 假设:
来源/目标表不得重叠、`writeFormulas` 不接受 R1C1、可续跑动作只有 5 个
(`main.py:1109-1115`:`writeValues`、`writeFormulas`、`setFill`、`setFont`、
`setNumberFormat`)。

**结论:只抽前端 HostAdapter 不构成打通。** 恢复与撤销必须按通道分别定义。

### 2.2 三套语义对照

| | Excel 当前工作簿 | WPS 本地文件 | 文件夹模式(openpyxl) |
|---|---|---|---|
| 身份 | `url:` + Office document url | 磁盘绝对路径 `.xlsx` | 工作目录内相对路径 |
| 身份稳定性 | 会话内稳定,另存即失效 | 路径即身份,改名即失效 | 相对路径 + 内容指纹 |
| 状态位置 | 内存(Excel 持有) | 磁盘(已保存文件) | 磁盘 |
| 恢复点 | 服务端 SQLite 账本 + 区域写前快照 | WPS `PluginStorage` 完整快照 | `.excel-bro-backups/` 文件级副本 |
| 权威现场 | 服务端账本 | 客户端 PluginStorage | 服务端 manifest |
| 撤销粒度 | 区域 | 区域 | 整文件原子替换 |
| 可续跑动作 | 5 个(`main.py:1109`) | 当前 0(整体重做) | 仅 `splitGroupAggregate`(B1) |

三者的快照来源、指纹算法、撤销机制全不同。这与项目既有定论一致:
**不要在两套语义之间架桥,让桥不必存在** —— 冲突时把分流点往前挪,
不在执行层做兼容翻译。

### 2.3 因此定三条硬规则

1. **共享层引入判别式 `WorkbookLocator`,但不改现有 `/api/office` 字段**:
   `{kind:"office-url"|"wps-path"|"folder-relative", value}` 只存在于
   `packages/core` 内部。Office 适配器在出网前把它序列化回原有 `url:` 字符串,
   服务端 `workbookIdentity: str` 与 `models.py:2008` 的校验保持不变。
2. **恢复接口按通道分开**,不合并成一个通用接口。Office 保持现有
   `/api/office/...`;WPS 恢复保持客户端权威(`PluginStorage`),服务端不参与。
3. **"可续跑"是 宿主 × 动作 的交集,不是动作属性**。Excel 的 5 个可续跑动作
   不自动等于 WPS 可续跑。

> 这是 v1 最大的缺漏。v1 把服务端当成已经中立的一层,实际上它带着 Office 语义,
> 且这些语义是对的(它们保护的是 Office 特有的内存态风险),不该为了"统一"而拆掉。

### 2.4 为什么不直接改接口字段(对第 2.3 条第 1 点的补充)

核实两端现状:

| 位置 | 当前类型 |
|---|---|
| `server/app/models.py:2008` | `workbookIdentity: str`,校验强制 `url:` 前缀 |
| `apps/excel-addin/src/contracts.ts:1172` | `OfficeExecutionState.workbookIdentity: string` |

**已落盘的 `OfficeExecutionState` 记录都是按字符串解析的。** 若把字段本身换成
判别式对象,受影响的不只是代码,还有服务端 SQLite 账本里已有的恢复现场 ——
旧记录会解析失败,正在挂起的任务失去撤销与续跑入口。

加上本方案已定"WPS 恢复不走服务端"(第 2.3 条第 2 点),这个接口**只有 Office
一个使用者**,把它泛化成联合类型没有换来任何收益,却要付兼容迁移的代价。

所以判别式只做**共享层的内部表示**:core 里用 `WorkbookLocator` 区分三种身份,
Office 适配器在调用 `/api/office/...` 前折叠成 `url:<...>` 字符串。
读到旧记录时反向解析为 `{kind:"office-url"}`,天然兼容。

若将来确有第二个使用者需要改接口,前置条件是:
(a) 旧客户端在字段变更后的行为定义;
(b) 已落盘账本记录的迁移或双读方案;
(c) 迁移失败时的回退。
三条齐备才可动,不在本次范围内。

## 3. 参数化列映射贯通验收(D→E 仅是测试实例)

### 3.1 为什么用它当第一条

"支持多少种动作"证明不了重复开发已消除。需要一条**同一份参数化需求、
同一组期望结果、三条通道各跑一遍**的用例。D→E 只是一组测试输入,
**不允许在运行时代码、提示词或协议里写死 D/E、`Sheet1` 或示例类别**。

首条共用能力是"按用户给出的映射表,把已授权源区域的值映射到目标区域"。
源工作表、源列/起止行、目标工作表、目标列/起止行、映射表、空值与未匹配值策略
都由本次需求和授权解析;源/目标区域必须形状相容,重叠写入在未定义
快照语义前拒绝。模型负责理解字段与规则,
本地确定性工具读取已授权的源区域并计算目标矩阵,最终仍生成现有白名单
`AnalysisPlan.writeValues`。原始数据行不进入意图模型,映射规则不进入运行时代码常量。
预览 → 用户确认 → 执行 → 校验 → 撤销保持同一闭环。

除 D2:D6→E2:E6 外,还需把相同数据移到另一张已授权表的 B2:B6、把目标改为
H2:H6 跑一组变形测试。两组只改参数与 fixture,不增加分支实现;
这能防止"测试通过,产品却只会 D→E"。

### 3.2 用例定义

**固定输入工作簿** `tests/fixtures/golden-column-map.xlsx`,`Sheet1`:

| | A | B | C | D | E |
|---|---|---|---|---|---|
| 1 | 订单号 | 日期 | 金额 | 类别 | 类别分组 |
| 2 | X001 | 2026-01-05 | 1200 | 办公用品 | (待写) |
| 3 | X002 | 2026-01-06 | 8600 | 电子设备 | (待写) |
| 4 | X003 | 2026-01-07 | 300 | 办公用品 | (待写) |
| 5 | X004 | 2026-01-08 | 450 | (空白单元格) | (待写) |
| 6 | X005 | 2026-01-09 | 2000 | 差旅 | (待写) |

第 5 行用于验证空白来源的映射策略,不是跨宿主"空串原样持久化"断言。
已核实 `openpyxl` 把 `""` 写入 `.xlsx` 后,保存并重新加载会读回 `None`;
因此不能要求三条通道都把持久化后的 `""` 与空单元格区分开。
第 1.1 节的误判问题另用负向比较测试固定,不能藏在这条正向用例里。

**指令**(映射必须写进指令,不能让模型猜):

> 「在已选工作表中,按这个映射把 D2:D6 的类别写入 E2:E6:
> 办公用品→行政,电子设备→资产,差旅→费用,空白→未分类;
> 未列出的类别先不要猜,请向我确认。」

映射规则、空白与未匹配策略显式给出,A1 才有理由要求 `plan`。
此 fixture 的 E2:E6 期望值是 `行政、资产、行政、未分类、费用`。
类别与列字母只属于测试数据,运行时从参数读取,不得写成行业规则。

### 3.2.1 配套用例:未给映射时必须澄清

同一 fixture,指令改为「按 D 列类别映射,把分组结果写到 E 列」(不含映射表)。

| 断言 | 期望 |
|---|---|
| B1 意图分类 | `clarification`,不是 `plan` |
| B2 澄清内容 | 询问映射规则与未匹配/空白策略;意图阶段不读取或列出 D 列原始值 |
| B3 未澄清时 | 不生成任何 `writeValues` 动作 |

两条用例合起来才完整:3.2 证明"给了规则会正确执行",3.2.1 证明"没给规则不会猜"。
按现有设计模型本应澄清,若它直接出计划,那是比空串更严重的缺陷。

**必须一致的断言**(两组列/表参数、三条通道逐条比对):

| 断言 | 期望 |
|---|---|
| A1 意图分类 | 显式规则可进入 `plan`;自动测试用固定模型响应/桩,真实模型另做意图抽检 |
| A2 模型输入 | 只含授权表结构,不含原始数据行 |
| A3 计划动作 | 本地计算后生成单个 `writeValues`,目标由参数给出;基准是 `Sheet1!E2:E6`,变形是另一张已授权表的 `H2:H6` |
| A4 授权集合 | 仅本轮明确选择的工作表,不因变形测试扩大 |
| A5 预览 | 执行前呈现完整 5 行待写值,可编辑 |
| A6 未确认时 | 不产生任何写入 |
| A7 执行后目标列 | 持久化重读后与用户最终确认的 5 行预览一致;基准为 `行政、资产、行政、未分类、费用` |
| A8 回读校验 | 正向用例通过;另见下方 `""`/`null` 负向比较测试 |
| A9 撤销后 | 目标区域回到执行前,源区域未被触碰 |
| A10 撤销前被外部改动 | 拒绝覆盖,不静默写回 |
| A11 预览被编辑后确认 | 重新生成并校验计划,确认绑定**编辑后**的最终计划,不是原始计划 |
| A12 预览与执行之间被改动 | 执行前重新核对工作簿身份、授权、源和目标区域状态;不一致即拒绝并要求重新预览 |

**空串回读负向测试独立于 A7/A8**:给比较器 `expected=[[""]]`、
`actual=[[null]]`,必须返回不相等;WPS 执行器 mock 在回读时把 `""` 变为 `null`,
不得报告 `verified`。如果真实宿主或文件保存格式无法区分这两种状态,
该通道不得承诺"严格验证空串写入";在计划预检时拒绝这种写入,
或将结果明确标记为 `executed_unverified` 并保留恢复资料,不得静默通过。

**A11/A12 补的是预览到执行之间的空窗**:A10 只守住了撤销前。
用户编辑预览后,旧计划和旧确认立即失效;从确认到首个写入之间工作簿仍可能被改动,
因此要复核来源与目标,而不是仅检查目标是否还能写。

### 3.3 三条通道的跑法

| 通道 | 执行方式 | 自动化程度 |
|---|---|---|
| Excel | Office.js 执行器 | 单测可覆盖计划生成与校验;真实写入需实机 |
| WPS | JSAPI 执行器 | 同上,实机需 12.1 目标版本 |
| 文件夹模式 | openpyxl | **可全自动**,无需宿主 |

文件夹模式的确定性转换、计划、执行与撤销可全自动,所以它是回归网的主力;
模型意图在自动测试中固定响应,真实模型另做抽检,不把不稳定的模型措辞当成
构建阻断条件。两个宿主的实机部分做成**临时工作簿测试清单**,
按 `docs/WPS_W*_VALIDATION_*.md` 既有格式留记录。

### 3.4 关卡含义

阶段 G 先建测试与记录基线,**允许尚未实现的功能和已知空串缺陷呈预期失败**。
这些断言用显式 expected-failure/隔离诊断机制记录,并锁定具体失败原因;
不得简单跳过。意外通过(XPASS)或换一种原因失败都应提示重新审查。
阶段 1/2 保持既有通过项不退化、已知失败项不新增或变形;
阶段 4 移除预期失败标记,要求 A1-A12、变形用例及负向测试
在对应通道全绿。在此之前不进行大规模编排迁移。

### 3.5 用户确认绑定

确认应绑定最终 `AnalysisPlan` 摘要、用户选择的工作表集合、工作簿身份、
来源区域指纹、目标写前状态及预览版本。用户修改预览后,必须重新生成摘要、
重跑白名单/授权/能力校验并重新确认;不能把旧确认沿用到新矩阵。
执行前任一绑定项不符就中止并重新预览,不自动扩权或按旧 `operationId` 重做写入。
各通道可采用不同恢复机制,但这些确认语义必须一致。

## 4. 能力矩阵:宿主 × 版本 × 动作(评审第 3 点)

### 4.1 当前状态

`config/capabilities.json` 的 `wpsWrite`:
`verifiedVersionPrefixes: ["12.1"]`、`allowedActions: ["writeValues", "clearRange:contents"]`、
`maxCells: 1000`。

问题:12.0 怎么验证、何时开放,文档没写;不支持的动作在**计划生成前**如何排除,
也没写 —— 现在是生成计划后在执行预检才拒绝(`wpsPlanExecutor.ts:225`)。

### 4.2 矩阵结构

```
hosts.<hostId>.versions.<versionPrefix>.actions.<actionType> =
  "supported" | "unverified" | "unsupported"
```

这是能力解析器的**目标形态**,不要求阶段 1 就重排配置文件。
阶段 4 前可从现有 `wpsWrite` 等配置导出等价视图;物理 schema 迁移单独验收。

三态定义:

| 状态 | 含义 | 行为 |
|---|---|---|
| `supported` | 该版本实机验收通过 | 可进计划 |
| `unverified` | 宿主可能支持,未验收 | **不进计划**,规划阶段即排除 |
| `unsupported` | 宿主 API 不具备 | 不进计划,且向用户说明原因 |

### 4.3 排除必须发生在规划前

这是对现状的实质改动。现在 WPS 的动作限制在执行预检(`wpsPlanExecutor.ts:225`),
用户会看到一个生成好的计划然后被拒。改为:

1. 规划请求携带宿主标识、完整版本和客户端检测到的可用动作,供规划时收窄;
   这些字段不构成授权凭据
2. **服务端取交集,不直接采信客户端自报** —— 根据可信配置解析该宿主/版本
   的动作上界,再与客户端集合求交。未知宿主、未知版本或未验收动作一律排除;
   客户端集合只能*收窄*,不能扩大
3. 规划器只在交集内生成动作
4. 执行预检**保留**现有拒绝作为第三道防线(不删,防矩阵与实现漂移)

第 2 步是安全要求而非工程洁癖:自报集合若被当成权威,一个构造过的请求就能让
规划器生成本不该开放的动作。三层的职责各不相同 —— 客户端收窄、服务端
按宿主/版本定上界、执行预检兜底实现漂移。服务端规划因此需要识别宿主,
但**不能**因此继承或放宽 Office 专属的恢复接口语义。

### 4.4 12.0 验收路径

12.0 不自动继承 12.1 的验收结论。开放流程:

1. 在隔离的临时工作簿和显式开发测试入口中跑第 3 节 A1-A12、变形用例
   与负向测试;`unverified` 期间不开放普通用户写入,测试入口不得被生产规划调用
2. 补 `docs/WPS_W*_VALIDATION_<date>.md` 记录,含版本号与实际读回值
3. 记录通过后才把 `"12.0"` 加入该动作的 `supported`
4. 未验收期间 12.0 用户看到明确说明,不看外观相同的空入口

### 4.5 两条不可动摇的约束

无论矩阵怎么演进:

- **所选来源表不可扩大** —— 未选的现有表不能被读取或写入。确需创建的新输出表
  必须在计划与预览中明示名称、影响与操作,由用户确认后才创建;
  不能把"执行前不存在"当成自动读取或扩权的许可
- **写入必须预览并确认** —— 任何通道、任何动作,无例外

## 5. core 边界与注入方向(评审第 4 点)

### 5.1 作废 v1 的论据

v1 用"App.tsx 里直接出现 Office API 只有约 17 行"推断大段流程可搬迁。
**这个论据不成立** —— 它只数了直接依赖,没覆盖间接依赖。

反例(v1 自己也发现了,但没意识到它否证了自己的论据):

- `intent.ts:130` `loadDictionaryForFormula` 内含 `Excel.run`,文件看起来是纯逻辑
- `dataTools.ts:295` `SheetReadRegion` 类型里直接持有 `Excel.Worksheet`;
  `:324` `readSheetIntoAccumulator` 收 `Excel.RequestContext`

正确的判定方式是**类型与调用图的传递闭包**,不是文本里出现几次 `Office.`。
改造前应先跑一遍依赖分析,把传递闭包里碰宿主的模块全部标出来。

### 5.2 分层与依赖方向

```
L0 contracts        纯类型。零运行时依赖
L1 pure             planCore / format / range / utils / tableSchema / modelSelection
                    纯函数,可直接单测
L2 semantics        验收判定 / 指纹 / preflight / planLiveness
                    纯逻辑,但依赖 L0 类型
L3 ports            HostAdapter / KeyValueStore / ApiClient / Clock 接口定义
                    只有接口,无实现
L4 orchestration    编排 hooks。依赖 L3 接口,不依赖任何实现
L5 ui               共用组件
```

**依赖只能从上往下,不得有反向边。**
L3 是全部环境依赖的收口处 —— 网络、存储、宿主、时间都在这里抽象成接口。
现有 `contracts.ts` 同时包含类型和运行时断言,不能整文件宣称为 L0;
抽取时把纯 DTO/类型放 L0,运行时校验放 L2,并保持前后端协议测试同步。

### 5.3 三个有环境依赖的模块怎么处理

评审指出 `api.ts`、存储、React hooks/UI 有环境依赖,不能简单归入 core。采纳:

| 模块 | v1 的处理 | v2 的处理 |
|---|---|---|
| `api.ts`(1146 行) | 直接进 core | 拆成 L3 `ApiClient` 接口 + 各 app 注入 `fetch` 实现。请求/响应**类型**进 L0,传输实现留 app |
| `storage.ts`(1000 行) | 直接进 core | 业务逻辑(迁移、校验、兼容推导)进 L2;`KeyValueStore` 是 L3 接口,Excel 注入 `localStorage`、WPS 注入 `PluginStorage` |
| hooks / UI | 直接进 core | 只有**已验证不碰宿主**的进 L4/L5,且必须通过 L3 接口取数据。碰宿主的改为接收 `HostAdapter` 参数 |

`PluginStorage` 已核实是同步的(`wpsHost.ts:43-47`),但 `getItem` 返回
`unknown`,适配器需做字符串强制并处理非字符串返回。

### 5.4 先做可验证的小范围抽取

不从 `contracts.ts`(1980 行,全仓依赖)开刀。第一刀选 L1:
`planCore.ts`(61 行,已是共享先例)+ `format.ts`(142)+ `range.ts`(54)+
`utils.ts`(104)+ `tableSchema.ts`(51)。

共约 400 行,零环境依赖,有现成测试。用它验证 workspace 配置、alias、
测试与构建链路是否真的通,再往上走。

## 6. 持久状态迁移(评审第 5 点)

### 6.1 连接 ID 必须是唯一键

核实 `server/app/llm/config.py:92` 已有 `connection:<id>` 形态,
`:363/:426` 按该前缀解析。既有设计是对的,迁移时**不能退化成按模型 ID 归并**。

风险:同一模型 ID(甚至服务地址也相同)允许存多条连接,各自有独立 API Key。
若以模型 ID 当唯一键,不同 Key 会互相覆盖。

两端共用模型配置时的规则:

1. 唯一键恒为 `connection:<id>`,模型 ID 只是展示属性
2. 目录按保存顺序显示 `(1)`、`(2)` 后缀,**后缀不写入模型 ID**
3. 模型调用只按连接 ID 解析凭据,不按模型 ID 选"第一条"

### 6.2 三类迁移与回退

| 状态 | 迁移 | 回退 |
|---|---|---|
| 旧 `local` 模型选择记录 | 目录加载成功后迁到有效连接 | 目录加载失败**不清空**已加载列表,不覆盖本机选择 |
| API Key | 见 6.4 | Key 不参与任何自动迁移;迁移失败保留原文件 |
| 撤销记录 | 见 6.3 | 双读 v1/v2,不删除旧记录;无法排除空串歧义时拒绝自动覆盖 |

### 6.3 撤销指纹必须版本化

`WpsUndoRecord` 已有 `version: 1`(`wpsPlanExecutor.ts:358`),但**指纹算法本身
没有版本标记**。严格写后验收与撤销指纹是两种判断,不能因修复前者就隐式
改变后者;若要升级指纹算法,必须先规定格式与兼容策略:

1. 新指纹字符串加算法版本前缀,如 `v2:<len>:<hash>`。v2 对单元格做
   稳定的类型编码,区分 `null` 与 `""`,仍优先记录公式;先用固定输入/输出向量
   锁定算法,不能只加前缀却沿用含糊的归一规则
2. 读到无前缀(v1)指纹时,用 v1 算法核对,**不以 v2 重算旧指纹**;
   记录格式也要双读 `WpsUndoRecord.version=1|2`,不能只改指纹字符串
3. 新执行一律写 v2;旧 `PluginStorage` 键的数据保留,迁移必须可回退
4. v1 记录在可证明写后状态未变时仍可撤销;若记录/现场涉及 `""` 与 `null`
   而旧指纹无法排除后续人工修改,保留恢复资料并报冲突,不得为了"兼容"
   静默覆盖用户数据

> 若直接改算法而不版本化,旧撤销记录会因指纹不匹配而失效;
> 若盲目沿用旧指纹,又可能对空串/空值变化失明。兼容目标是
> "旧记录仍可读取、无歧义时可撤销、歧义时安全拒绝",不是保证每条旧记录必然写回。

### 6.4 API Key 的实际流向

新增或替换连接时,前端会把**用户本次输入的新 Key**提交到本机后端;
否则无法保存连接。后端只在本机受保护配置中持久保存,读取既有配置时
前端只收到连接 ID、`apiKeyConfigured` 与脱敏提示,**不回显旧 Key**。
前端不得把本次输入写入 `localStorage`、任务日志或诊断;表单关闭时清理草稿。
共享模型目录不按模型 ID 合并连接,也不把 Key 作为自动迁移数据经前端搬运。

## 8. 本计划的范围决定与后续议题

1. **WPS 恢复权威维持客户端** —— 本计划不把 WPS `PluginStorage` 现场迁往
