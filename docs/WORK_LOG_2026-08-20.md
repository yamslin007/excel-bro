# 工作日志 2026-08-20

## 问题诊断：/function 公式生成不可靠

### 问题表现
用户使用 /function 生成"根据问题类型填入错误级别"的公式时，出现三类错误：

1. **映射不完整**：字典表有 6 种问题类型，生成的公式只包含 2 种
2. **值错误**："空间方向" 应该是 p0，公式写成了 p1
3. **逻辑颠倒**：用 `SEARCH("p0", D2)` 搜索输出值，而非搜索关键词

### 场景说明
- **评分表.xlsx**：D 列是问题类型（可能包含多个，逗号分隔），E 列要填公式
- **tt.xlsx**（字典表）：A 列是 6 种问题类型，B 列是错误级别（"/"、"p0"、"p1"）
- **需求**：检测 D 列包含哪些关键词，按 p0 > p1 > / 的优先级返回最高级别

### 根因分析

#### 当前设计的根本缺陷
让模型"端到端生成完整公式文本"导致：

1. **模型会"清洗"数据**：
   - "/" 被语义理解为空值 → 替换成 ""
   - 看到样本数据只有 2 条 → 以为只需要生成 2 条判断
   - 把输出值当关键词 → 逻辑完全颠倒

2. **Prompt 无法解决**：
   - 已经有 14 条规则 + 明确说明"/" 是字面值必须保留
   - Claude 能生成逻辑正确的公式（覆盖全部 6 种类型，"/" 保留）
   - 但 Claude 选择了**硬编码关键词**而非**引用字典表区域**
   - 即使成功率提升到 95%，但 5% 失败率对于工具来说不可接受

3. **信息过载**：
   - 模型需要理解场景 + 提取字段 + 生成两版公式 + 处理边界情况
   - 认知负载过高，失误是必然的

### 正确的方案：两级架构

#### 核心原则
**模型擅长语义理解，代码擅长精确生成 → 各司其职**

#### 设计
```
第一级：模型分析场景（返回结构化 JSON）
输入：用户需求 + 表结构
输出：{"scenario": "priority_keyword_match", "sourceColumn": "D", ...}

第二级：代码生成公式（零失误）
输入：场景分析结果
输出：精确的公式文本（引用完整区域，不硬编码值）
```

#### 支持的场景
1. **lookup**（精确查表）→ XLOOKUP/VLOOKUP
2. **priority_keyword_match**（优先级+关键词）→ SUMPRODUCT 嵌套
3. **keyword_match**（关键词分类）→ ISNUMBER+SEARCH
4. **calculation**（数学计算）→ 四则运算
5. **complex**（复杂逻辑）→ 回退到现有模式

#### 实施文件
已创建详细方案：`FORMULA_REFACTOR_PLAN.md`

包含：
- `server/app/formula_analyzer.py`（场景分析器）
- `server/app/formula_generator.py`（公式生成器）
- `server/app/rule_generator.py`（主流程改造）

### 预期效果

#### 改造前（当前）
- ✗ 成功率 ~70%
- ✗ "/" 等字面值被替换
- ✗ 映射不完整

## 技术思考

### 关于 AI 辅助代码生成的抽象层次

**错误的抽象**：让 AI 生成完整的、需要 100% 精确的代码
- AI 是概率生成器，95% 正确 ≠ 可用
- Prompt 工程无法解决本质问题

**正确的抽象**：让 AI 理解语义，代码负责精确性
- AI 擅长：理解用户意图、识别场景、提取关键信息
- 代码擅长：精确生成、语法正确、完整性保证
- 参考项目中的 `crossTableFormula.ts`：模型判断 → 代码拼串

**适用场景**：
- SQL 生成：AI 识别查询意图 → 代码生成 SQL
- 正则表达式：AI 理解匹配规则 → 代码生成 pattern
- Excel 公式：AI 分析场景 → 代码生成公式文本

这次改造是一个很好的"正确抽象"实践案例。

## 设计原则回顾

用户说："这个对我很重要，/function 对人类很重要，这是 excel 工具构建的关键一环，你必须认真对待。"

**回应**：
1. 停下来测量真实失败率（不对着 3 个样本点猜整个系统）
2. 看清问题本质（职责错位：让模型搬运数据）
3. 系统性设计（降维打击，而非猜着改 prompt）
4. 可测量的效果（结构化场景 100% vs 当前 ~70%）

**核心洞察**：
- 没有测量就没有诊断
- 不要让 AI 干它不擅长的事
- 正确的抽象比堆规则重要
- 可靠性来自设计，不是 prompt 工程
