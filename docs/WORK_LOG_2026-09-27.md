`ShapeMismatchError`。理由统一是「猜错的分类在单元格层面看不出来」。

### 3.1 障碍一：加载项打不开 —— 已解决

点功能区按钮无反应，控制台：

```
Main resource content verification failed: http://127.0.0.1:3889/index.html
@vite/client:1   Failed to load resource: 404
@react-refresh:1 Failed to load resource: 500
ReferenceError: ribbon is not defined
```

根因：跑的是 `npm run dev`（= 裸 `vite --port 3889`），而实机调试**必须**跑
`npm run debug`（= `wpsjs debug -p 3889`）。后者除了起资源服务，还会**向 WPS
登记开发加载项**；缺了登记，QtWebEngine 拒绝执行模块，`main.tsx` 从不运行，
`window.ribbon` 从不赋值。`docs/WPS_PERSONAL_EDITION_ADAPTATION_GUIDE.md:347`
早已写明走官方 wpsjs 通道。

两个坑一并记下：

1. `wpsjs debug` 会把 vite 作为**子进程**拉起，命令行一模一样，
   **光看 `vite --port 3889` 分辨不出两者**，必须看有没有 wpsjs 父进程。
2. **功能区图标能正常显示不能证明 JS 已加载。** 图标来自 `ribbon.xml` +
   `GetImage` 的宿主侧缓存，与 `main.tsx` 是否执行无关。我一度拿它当加载成功的
   证据，推理不成立。

### 3.2 障碍二：版本闸配置错误 —— 未解决，待证据

M2（`map_column_values` → 单个 `writeValues`）返回：

```
当前 WPS 版本「12.0」尚未通过写入能力验证。
```

`wpsPlanExecutor.ts:229` 读 `application.Version`，与 `capabilities.json` 的
`verifiedVersionPrefixes: ["12.1"]` 比前缀。**真实宿主返回 `"12.0"`。**

而 `12.1.0.28488` 是**产品版本**，来自安装路径
（`...\WPS Office\12.1.0.28488\office6\et.exe`，已从运行进程确认）。
`docs/WPS_W3_A_VALIDATION_2026-09-23.md:16` 当初写白名单用的正是这个数字，
但代码比的是另一个字段 —— WPS 模仿 Excel 对象模型，`Application.Version`
很可能给的是 Excel OM 兼容级别，与产品版本不是一套编号。

**结论：这道闸从来没在真实宿主上通过过。** 五个测试替身全都写死了产品版本：

```
apps/wps-addin/src/WpsAgentPanel.test.tsx:405 / :473   Version: "12.1.0.28488"
apps/wps-addin/src/wpsEmptyStringBaseline.test.ts:60   Version: "12.1.0.28488"
apps/wps-addin/src/wpsPlanExecutor.test.ts:58          Version: "12.1.0.28488"
apps/wps-addin/src/wpsWriteCapabilities.test.ts:17     Version: "12.1"
```

103 条 WPS 测试全绿，是因为它们共享同一个错误假设。替身的值是人编的，不是从
宿主取回来的，所以测的是「如果宿主这么报就能过」，不是「宿主确实这么报」。

**故意没有直接把白名单改成 `["12.0"]`。** 缺一个关键证据：
`Application.Version` 能不能区分 WPS 的不同产品版本。如果所有 WPS 版本都返回
`"12.0"`，改了等于**把闸门变成永真** —— 门还在但不挡任何东西，比现在的误报关闭
更糟（现在是保守失败，改错是静默放开）。

待办：在宿主控制台枚举 `Version`/`Build`/`Name`/`wps.Env.GetAppVersion()` 等，
找出哪个字段带 `12.1` 或 `28488`。

- 找到了 → 闸门改读那个字段，白名单语义不变。
- 找不到 → **这道版本闸的设计本身要重做**。拿分辨不出版本的字段做版本白名单
  没有意义，应改为按能力探测（`wpsWriteCapabilities.ts:88-115` 那批
  `Range`/`Formula`/`MergeCells`/`ProtectContents` 实测已经在做这件事）。

M2 记为**未通过，原因是版本闸配置错误，不是映射路径的问题** —— 映射路径这一轮
根本没被执行到，`prepareWpsPlan` 在第 230 行就抛了，连计划预览都没轮到。

### 3.2.1 顺带：M11 意外先过了，而这暴露了清单本身的一个假设

`STAGE_G_BASELINE_2026-09-26.md:131` 写的是：

> WPS 侧另需：M11 未验收版本**（如 12.0）**应明确拒绝并说明原因，不出现外观
> 相同的空入口。

清单作者把 `12.0` 当作「未验收版本」的举例。而实机 `Application.Version` 报的
**正好是 `12.0`**。所以：

- M11 的**拒绝路径**事实上已经验证通过 —— 报错明确、带原因、没有外观相同的
  空入口，符合验收标准。
- 但它拒绝的是**我们本来要用来验证 M2-M10 的那台机器**。

这说明当初写清单和写白名单的时候，「12.0」和「12.1」被当成了两个不同产品版本，
而它们很可能是同一台机器上两个不同字段的值。M11 原本的意图是「拿一台真正的旧
版本来试」，现在无法用这台机器完成 —— 修好字段之后，M11 需要重新设计场景，
而且要避免用「临时改 `verifiedVersionPrefixes`」来伪造：那测的是配置生效，
不是真实版本差异，如果这么做必须在记录里写明。
