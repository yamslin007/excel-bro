## 1. 当前项目事实与缺口

下表是 2026-09-09 的代码核对结果。B1 已包含真实子进程强制退出测试；尚未进行真实 Excel 宿主、安装包和断电实验。行号可能随开发变化，应以符号定位为准。

| 范围 | 当前代码依据 | 当前能力及不足 |
| --- | --- | --- |
| 文件夹进度任务 | `server/app/task_ledger.py`、`server/app/main.py` | SQLite 持久保存身份、事件、checkpoint、终态和幂等墓碑；进程内表只作为活跃任务热状态 |
| 文件夹执行重连 | `folder_execute_stream`、`folder_execute_status`、`folder_execute_resume_stream` | 相同 operationId/请求指纹可补收事件和终态；B1 对有完整产物与指纹证据的拆分发布允许显式续跑 |
| 前端重连 | `apps/excel-addin/src/App.tsx`、`api.ts` | 保存 operationId/turnId，刷新或断线后先查持久状态；不会因连接失败自动创建新的写入或规划任务 |
| 重载后挂接 | `App.tsx`、`conversation.ts` | 文件夹执行和预算暂停卡可在重载后查询原任务；`resuming` 临时状态会恢复为可再次核对的 `pending` |
| 规划状态 | `task_ledger.py`、`turn_state.py` | 流式规划的请求、事件、checkpoint、预算、终态持久化；TurnRegistry 仍保留进程内热缓存，兼容非流式 `/api/plan` 不具备 B2 恢复保证 |
| 模型循环 | `excel_agent.py`、`agent_loop_protection.py` | 保存 messages、LoopState、工具缓存、开放工具模式、修复状态、下一轮位置和完整待处理模型响应；只在安全边界暂停 |
| 模型重试 | `server/app/llm/client.py`：`chat_completions` | 有同一连接的有限重试；不是跨进程恢复或本方案的备用模型调度 |
| 文件夹动作 | `folder_workbooks.py`：`_execute_folder_plan`、`resume_folder_plan` | B1 仅支持单个 `splitGroupAggregate` 的完整计算产物暂存和逐文件发布续跑；其他动作仍不按步骤号跳过 |
| 文件夹保存与恢复 | 同文件的暂存、publish checkpoint 与 manifest 逻辑 | 每个目标记录暂存产物、写前/写后指纹和发布状态；重启后先核对实际文件，只发布仍为写前态的目标，不重新计算 |
| 并发保护 | `main.py`、`folder_write_guard`、任务账本 CAS | 规范化工作目录具有进程内和跨进程排他；继续请求按 revision 领取，恢复点仍受生命周期保护 |
| 应用数据目录 | `server/app/app_data.py`、`packaging/runtime.py` | 开发/安装共用应用数据解析；SQLite 账本位于本机应用数据，工作簿大产物仍在已登记工作目录 |
| 文件刷新 | `folder_workbooks.py`：`_atomic_write_manifest`、`_save_workbooks_atomically` | manifest 已执行 flush、fsync、替换和占用重试；工作簿临时输出没有同样的显式 fsync，整链路断电耐久性未验证 |
| 当前工作簿动作 | `apps/excel-addin/src/excel.ts`：`executePlan` | 循环执行动作并同步到 Excel；异常可返回部分撤销资料，没有持久化节点调度器 |

现有相关测试包括：

- `server/tests/test_main.py::test_folder_execute_stream_reuses_operation_without_writing_twice`。
- `apps/excel-addin/src/api.test.ts` 中的 `reconnects with the same operationId and forwards progress`。
- `server/tests/test_folder_workbooks.py` 的验证失败后撤销、回滚失败保留救援副本、外部修改后拒绝撤销等测试。
- `test_split_group_resume_after_real_process_exit_before_publish` 的真实子进程退出与逐文件恢复发布。
- `server/tests/test_agent_integration.py` 的完整模型响应后暂停、恢复时复用响应且工具只调用一次。
- `server/tests/test_main.py` 与 `test_task_ledger.py` 的规划暂停、刷新/重启持久化、CAS 修订和稳定 requestId 去重。

这些测试能证明受支持路径的重连或恢复行为，不能代替真实 Excel、安装环境和断电测试。

`progress.folderOperationTtlSeconds=3600` 现在只控制进程内热缓存；SQLite 终态保留期由 `taskRecovery.operationRetentionDays` 控制，清理载荷后仍保留幂等墓碑。未知或过期 operationId 不会进入创建分支重做写入。非流式文件夹兼容入口也经过相同持久准入与目录排他。

规划默认仍受 8 轮和 20,000 token 硬限制。流式规划在**累计活跃执行总时限**
（`planningHardWallTimeSeconds`，默认 1800 秒）内自主运行；`planningReminderSeconds`（60 秒）
只是非阻塞的耗时提醒，不触发暂停、不弹"继续"按钮。到总时限后不再启动新的模型/工具
调用并如实说明。`llm.timeoutSeconds=60` 是独立网络等待配置。继续只接续现场，不提高
token、轮次或连续错误上限。

当前恢复仍有明确边界：文件夹节点级续跑限于单个 `splitGroupAggregate`；规划恢复限于 `/api/turn/stream`，工具检查点只落在完整单次工具调用之后；备用模型只允许用户从已配置连接中显式选择；Office.js 只支持已保存工作簿中的 `writeValues`、`writeFormulas`（非 R1C1 铺满）、`setFill`、`setFont` 和 `setNumberFormat`，且暂不开放来源表原地修改。任意 DAG/子任务、结构或复杂对象动作以及通用取消仍未实现。持久目录索引只用于定位已登记目录，不能替代当前授权。

## 2. 目标、定义与不变边界

### 2.1 目标

- 前端断线不影响仍正常运行的后台任务；重连可以补收进度和最终结果。
- 服务异常退出后，可以找回未完成任务，确定哪些结果可复用、哪些步骤需要重算。
- 已产生的 Excel 写入不会仅因“没收到成功消息”被盲目重复执行。
- 可恢复的任务继续到完成；结果不确定的任务明确进入核对流程。
- 规划阶段可在允许的模型之间接续；已确认的确定性计算和写入不依赖模型持续在线。
- 达到可追加的运行预算时保存现场，向用户说明进展并询问是否继续；延长预算与授权 Excel 写入分开处理。

### 2.2 术语

| 术语 | 本文含义 |
| --- | --- |
| checkpoint | 能重建应用层任务现场的一致记录及其有效产物引用 |
| 节点完成 | 已满足该节点的完成契约，且恢复所需结果与状态已可靠保存 |
| 挂起 suspended | 当前不继续执行，但保留原因、资料和恢复入口 |
| 恢复核对 reconciling | 对比记录与真实文件/宿主状态，决定能否继续 |
| 续跑 resume | 复用有效检查点，从下一个可执行节点或重试单元继续 |
| 重算 recompute | 对没有外部写入的确定性单元重新计算，可能重复部分工作 |
| 回滚 rollback | 将实际文件恢复到已确认的先前状态，不等于切换任务检查点 |
| 进度事件 | 给界面的展示记录，不单独作为节点执行成功的证据 |

恢复的是可序列化的应用状态。Python 调用栈、协程、文件句柄、Office.js 代理对象和模型内部生成状态不属于可直接恢复的现场。

### 2.3 沿用项目边界

- 模型负责语义判断；本地受控工具负责读取和计算。
- 授权只来自用户选择的文件和工作表，恢复不能自动扩大。
- 意图阶段仍不向模型发送原始数据行。
- Excel 写入必须来自白名单 AnalysisPlan，先预览，再明确确认。
- 不新增任意脚本、宏、VBA 或模型可调用的外部程序执行。
- 不硬编码行业字段、业务数据或客户名称。
- 协议修改同步 `contracts.ts` 与 `server/app/models.py`；限额集中在 capabilities。
- 当前工作簿与文件夹模式分别声明可恢复能力，不互相借用未实现的保证。

## 3. 总体结构、收益与实施前置条件

建议在现有 Python 服务中增加任务存储、恢复调度和节点执行适配。前端负责展示和用户操作；Office.js 动作仍在所属 Excel 宿主执行。服务无需先迁移到其他 Agent 框架。

首次按有序依赖链实现，保留依赖字段。现有 AnalysisPlan 是顺序动作列表，不能未经依赖分析就并行执行。Agent 多轮工具循环通过轮次和稳定节点身份记录，不强行表示为一个不允许循环的静态 DAG。

同一模型响应产生的多个工具调用，应先完整登记，再逐项执行；已完成的工具结果不能因同批后续工具失败而全部重跑。子任务仅保存父子关系、输入输出和状态，首期不实现任意递归子任务调度。

### 3.1 三阶段范围

- 阶段 A：持久身份、中断发现、安全核对和受控恢复。任务、文件、恢复三层互斥同时落地。此阶段不宣称能续跑。
- 阶段 B：在已验证边界开放真实续跑。B1 优先文件夹暂存/发布/验收；B2 实现预算暂停继续及其必需的最小规划现场持久化，不用只有按钮、没有现场的方式交付。
- 阶段 C：按测量收益扩展细粒度规划/查询检查点、备用模型接续及 Office.js 动作级恢复。

各阶段实施清单、依赖和退出条件见第 15 章。不能把阶段 C 的任意规划恢复推迟，解释为阶段 B2 可以不保存自己的消息和工具结果。

### 3.2 收益评估

按规划、读取/计算、发布、验收分别统计中断频率，实际有效运行耗时的 P50/P95/最大值，重复 token/费用或未知用量，以及需要用户重复澄清的次数。文件夹样本按文件数、行数和输出规模分档。记录所选粒度增加的序列化耗时、磁盘峰值、可复用比例和恢复耗时。

测量决定是否保存每个计算中间态、每页查询和完整工作簿，不把每条进度都做成检查点。意图登记、防重复写入、恢复互斥属于安全前置，不因收益尚未量化而删除。不得再用“60 秒以内”代替真实成本测量。

### 3.3 实施前决策门槛

| 门槛 | 必须交付的内容 | 阻塞范围 |
| --- | --- | --- |
| 单一调度权威 | 第 12 章协议对应的存储方案、原子提交方法、崩溃窗口及迁移决策记录 | 阶段 A 的持久任务与写入 |
| 任务与文件身份 | task/operation/恢复身份映射，路径别名及多服务实例互斥策略 | 阶段 A 的写入与恢复 |
| 来源版本 | 每类支持节点的输入证据、失效依赖、重算位置和重新确认规则 | 阶段 B1/B2 |
| 预算协议 | 追加份额、总上限、次数/轮次/token 联动、无进展停止规则 | 阶段 B2 |
| 收益基线 | 代表性样本和粒度选择依据，不要求先收集长期生产数据 | 细粒度检查点与阶段 C |

上述属于待关闭的设计项，不交给运行时模型自由决定；本版不据此宣称可以直接跳过协议设计开工。

### 3.4 控制流程

```text
用户请求
  → 持久登记任务、授权和请求身份
  → 规划/只读节点
  → 回答，或等待计划确认
  → 确认后的执行节点
  → 核对结果并完成

异常/原执行者失联/预算提醒
  → 暂停调度并保留现场
  → 领取恢复核对权
  → 核对记录、授权、输入和实际写入
  → 继续 / 等待用户 / 恢复文件 / 明确失败
```

用户关闭进度界面不等于取消任务。用户明确取消后，启动扫描不得自动将任务改回 running。

## 4. 节点边界与 checkpoint 时机

### 4.1 粒度建议

| 类型 | 合适的节点边界 | 恢复方式 |
| --- | --- | --- |
| 模型调用 | 一次完整、可解析的响应 | 保存响应与待处理工具调用；响应不完整则重发该轮 |
| 只读工具 | 一次有确定输入版本的查询或分页单元 | 复用已保存结果，或从稳定输入重算 |
| 分块聚合 | 一批数据与对应累计统计同时完成 | 保存游标、累加器和输入版本的一致组合 |
| 内存工作簿处理 | 一段计算及可重新加载的工作簿状态 | 保存一致中间工作簿，或声明整段可重算 |
| 文件发布 | 一个目标文件的替换及内容核对 | 先核对是否已应用，再决定补记或重试 |
| Office.js 动作 | 可核对的一步或同步批次 | 经动作专用的结果核对后恢复 |
| 验证 | 一组可重复读取的验收条件 | 可以重跑验证，不重放写入 |

拆分任务可先实现：读取稳定输入 → 计算完整分组结果 → 生成暂存工作簿 → 暂存验收 → 文件发布 → 最终验收。

不得把每条 SSE 消息、每张输出表进度或界面步骤序号自动提升为恢复节点。

### 4.2 只读或计算节点的提交顺序

1. 持久登记节点输入、调用身份和 running 状态。
2. 执行计算，生成受控产物。
3. 将产物写入不可变版本文件，完成所声明持久化等级的刷新，并校验长度、内容摘要和格式。这是新增实现要求，不是现有工作簿输出已经具备的能力。
4. 通过任务存储的一次原子提交，记录产物引用、节点完成、checkpoint、预算增量、下一可执行节点和对应完成事件；JSON 与 SQLite 的具体实现均须满足第 12 章契约。
5. 提交成功后才对外声明该节点可恢复。

若产物已落盘而任务记录未提交，它只是尚未引用的候选产物；可校验后收用或清理，不能直接视为完成。

首期声明范围仅为通过故障实验的进程退出/重启恢复，不声明断电保证。现有 manifest 的 flush/fsync 不证明工作簿、目录项和存储设备整体同步；即使补充产物刷新，也须另做平台与断电验证。恢复必须同时处理“记录领先文件”和“文件领先记录”，不能偏信一方。

### 4.3 写入节点额外要求

写入前必须持久保存执行意图、目标身份、参数摘要、执行前条件、预期效果以及恢复资料引用。先保证登记成功，再允许产生外部写入。

流程为：登记意图 → 准备恢复资料/输出 → 标记 applying → 执行写入 → 核对实际效果 → 保存写入回执与 checkpoint。

“保存节点完成”可以证明文件已发布并匹配字节指纹，不代表业务验收通过。最终验收属于独立节点；验收失败时保留“已写入”事实和恢复入口。

### 4.4 崩溃窗口必须逐项处理

| 中断位置 | 恢复处理 |
| --- | --- |
| 登记意图前 | 不允许已产生写入；若有写入即为实现缺陷 |
| 意图已登记、动作尚未开始 | 检查执行前条件后重试 |
| 中间产物落盘、checkpoint 尚未提交 | 核验候选产物，或从最近有效计算检查点重算 |
| 外部写入发生、完成回执尚未保存 | 核对真实目标；不得根据任务记录未完成直接重放 |
| checkpoint 已提交、客户端未收到事件 | 返回已提交结果，补发事件 |
| 文件发布完成、最终验收尚未执行 | 从验收节点继续，不再次发布 |
| checkpoint 写入失败或磁盘空间不足 | 停止后续调度；已发生的写入进入核对流程 |
| 完成记录存在，但产物缺失或文件仍是写前态 | 拒绝按完成标记跳过；进入核对，不擅自重新写入 |

退回旧 checkpoint 不会撤销已经落盘的动作。选择更早计算检查点时，也必须先处理从该点之后已发生的所有写入。

## 5. 持久化现场的数据结构

以下字段为逻辑设计，尚未加入现有协议；具体字段命名在实施前统一。

| 对象 | 最低必要信息 | 关键约束 |
| --- | --- | --- |
| Task | taskId、模式、请求摘要、状态、revision、创建/更新时间 | taskId 在恢复期间保持稳定 |
| Plan | 完整白名单计划、planVersion、planHash、执行器版本 | 已确认计划不可原地改写 |
| Authorization | 已登记根目录身份、文件/表身份、范围摘要、授权修订 | 不持久复用过期会话或短期令牌作为权限依据 |
| Approval | 计划哈希、输入约束、输出目标、用户确认记录 | 改目标、改语义或扩大范围后失效 |
| Node | nodeId、依赖、轮次、类型、状态、恢复策略、输入摘要 | 不使用界面 sequence 作为唯一节点身份 |
| Checkpoint | checkpointId、父检查点、generation、已完成集合、下一节点、上下文与产物引用 | 只引用已验证存在的版本 |
| Context | 最终确认需求、澄清记录、messages、工具调用与结果配对、摘要、结构化工作记录 | 确认口径和授权不依赖摘要推断 |
| ToolReceipt | 本地稳定调用 ID、工具/版本、参数哈希、输入版本、结果引用、完整性 | 重试不改变逻辑调用身份 |
| Artifact | artifactId、受管相对路径、类型、大小、内容指纹、生成节点、版本 | 路径只是定位信息，不证明内容有效 |
| WriteReceipt | 幂等键、目标身份、前后指纹、实际名称、应用状态、恢复点引用 | 与实际文件状态共同判断是否已执行 |
| Exception | 错误类别、节点/阶段、脱敏信息、尝试次数、结果确定性、重试时间、fallback 记录 | 区分可重试与必须核对 |
| Budget | 累计轮次、token、未知用量、有效运行时间、重试次数、提醒阈值、已批准额度、总上限、追加历史 | 恢复不能重置预算；追加按稳定请求 ID 幂等登记 |
| Ownership | executorId、领取修订/尝试令牌、任务锁与目标锁归属；可选心跳 | 不强制分布式 lease；旧执行者不得提交或继续写，心跳不是接管许可 |
| RecoveryDecision | 恢复方案 revision、方向、目标集合、前后证据摘要、确认记录、恢复操作 ID | 继续发布与恢复文件互斥；恢复本身也可中断并核对 |
| RootRegistration | 已登记目录 ID、受管位置、路径安全信息、访问策略 | 只用于定位和重建检查，不代替当前授权 |
| Event | taskId、operationId、稳定 stepId、单调 sequence、可见安全摘要 | 状态变更与完成事件一起提交 |

身份关系建议：

- taskId：一项用户任务的生命周期。
- turnId：兼容现有规划请求关联；映射到 taskId，不能代替所有执行身份。
- operationId：一次已确认执行的稳定外部身份，重连与续跑复用。
- executionId：与实际执行及恢复点关联；恢复同一次发布不得每次新建一套副本。
- attemptId：一次尝试的诊断身份；改变它不能绕过幂等。
- planVersion：语义或执行目标变化时递增，保留旧版本和历史写入记录。

scratchPid 若表示 scratchpad，建议改用结构化工作记录及 scratchpadRef；若表示操作系统 PID，只用于诊断。摘要及工作记录保存已确认事实、工具证据和待办事项，不把模型隐藏推理或进程内存当作恢复契约。

## 6. 状态机与错误策略

### 6.1 分开记录三类状态

- 任务调度状态：queued、running、waiting_user、suspended、reconciling、completed、failed、cancelled。
- 写入效果：none、prepared、applying、applied、unknown、rolled_back。
- 验证结果：not_run、passed、failed、unverified。

这些是拟议内部状态，不要求全部暴露给用户。任务结束、写入成功和业务验收成功必须能分别表达。界面可显示“已写入，验证未通过”。

节点使用 pending、running、committed、suspended、failed 等最小状态；committed 表示节点契约已提交。对部分成功的多文件任务，还需保存每个文件的独立结果。

预算暂停使用持久的 pauseRequested 与 pauseReason：到阈值时先请求暂停，安全边界保存成功后才置 waiting_user / budget_extension。保存失败进入 suspended / checkpoint_error，不能显示“已保存，可继续”。业务需求确认、写入确认和预算追加使用不同的等待原因及确认记录。

### 6.2 suspend 与进程崩溃

可捕获异常由执行器记录后挂起。强制结束进程时依赖上一次已提交状态、执行者身份和启动扫描发现遗留任务，不能要求崩溃进程先成功写出 suspended。

连接状态独立维护：前端断线而后台仍在运行时，继续后台任务并允许重新订阅。仅凭界面失联不得开启第二个执行者。

### 6.3 错误分类

| 错误 | 默认策略 |
| --- | --- |
| 模型网络超时、暂时限流、服务暂不可用 | 有限退避重试；满足策略时切换允许的备用模型 |
| 模型凭据失效、连接被删除 | 挂起；修复配置或选择允许的连接 |
| 模型计划结构错误 | 受限纠正；保留连续错误和累计预算，不无限循环 |
| 授权缺失、来源变化、目标冲突 | 等待核对或重新预览，不自动扩大授权 |
| 文件占用、空间不足，且确定未写入 | 释放条件后从对应安全节点继续 |
| 文件/Office.js 写入结果未知 | reconciling；没有可靠判定时保持挂起 |
| checkpoint 或关键产物损坏 | 使用可验证的较早计算结果或进入人工恢复，不能假装成功 |
| 用户取消 | 记录取消意图，在安全边界结束；明确是否已产生写入 |
| 业务验证不通过 | 报告具体差异与写入事实，保留恢复入口 |

正在发生文件替换时，取消请求需先记录，再完成该临界操作的核对或回滚；不能直接报告“没有修改”。

## 7. 恢复调度与幂等

### 7.1 恢复算法

1. 找到持久任务，并核对任务归属、记录格式和版本兼容性。
2. 以任务存储的条件更新取得唯一恢复资格及目标互斥权；核实旧执行者已停止相关写入。
3. 保持已确认的计划版本，加载 checkpoint、消息、调用回执和产物引用。
4. 重新建立受控文件会话或 Office.js 宿主连接；不直接复用失效 sessionId、句柄或令牌。
5. 核对任务授权、来源约束、目标身份、产物指纹与恢复资料。
6. 优先处理 applying/unknown 节点及已有写入；在核对前不调度依赖节点。
7. 复用已提交且仍有效的结果；缺失的纯计算结果按依赖失效传播规则重算。
8. 恢复待执行工具调用、模型轮次和预算；满足条件时选择备用模型。
9. 从第一个依赖满足的节点继续，逐节点提交新的 checkpoint。
10. 最终验收后记录任务结果，前端补收同一任务事件。

checkpoint 恢复不是恢复某个网页的滚动位置。聊天历史恢复也不能代替这些步骤。

### 7.2 幂等键

建议逻辑键为 taskId + planVersion + nodeId，发布节点再区分稳定目标身份；同时绑定参数哈希、工具版本和输入版本。

同一键出现不同请求内容应返回冲突，不允许覆盖旧记录。重试、刷新、服务重启和换模型不改变同一动作的逻辑键。用户确实新发起相同需求时可以创建新 taskId，但不得把“恢复”伪装为新任务。

若用户确认采用新输入版本重算，应持久创建新的节点输入修订（并在改变语义/目标时更新 planVersion），纳入相应逻辑键，保留旧结果和写入回执。不得用一次普通重试覆盖同一键绑定的旧输入；新修订生成前仍须处理已有副作用。

已结束任务可以清理大产物，但幂等状态不能直接随进度 TTL 被遗忘。保留轻量完成/取消/过期标记；旧恢复请求应返回明确结果或已过期，不能隐式创建新执行。

创建与恢复协议必须分开：只有明确的新任务创建请求可以生成身份；resume、事件订阅、预算追加和状态查询遇到未知身份都拒绝创建。新建执行需绑定未消费且仍有效的执行确认身份，不能仅凭客户端换一个随机 operationId 就再次消费同一次确认。明确的新任务/新执行确认仍允许用户再次运行相同内容，不能用文本相同永久去重。

旧版本只有内存 operation 的请求不具有持久幂等证据。升级后遇到这种旧恢复请求，返回需核对/已过期，不能回退到新执行接口。即使清理了轻量标记，未知恢复请求也保持拒绝，因此不会因标记删除重新变成合法创建。

### 7.3 实际写入的核对

| 当前真实状态 | 处理 |
| --- | --- |
| 匹配可靠的预期写后状态，且身份、作用范围一致 | 补记应用完成；依节点契约继续验证或后续步骤 |
| 匹配执行前状态，且可证明未产生其他副作用 | 允许重试原动作 |
| 一部分目标已应用 | 逐目标核对，按确认策略继续剩余发布或回滚 |
| 与写前、写后均不一致 | 视为外部修改、部分写入或未知状态，挂起 |
| 只知道“同名表存在”或“文件存在” | 证据不足，不能判定动作已完成 |

不把 operationId 或一个 completed 标志描述为跨数据库、文件系统和 Excel 宿主的全局“只执行一次”保证。目标是通过持久身份、受控重放和效果核对，让支持的动作恢复后不出现重复副作用。

### 7.4 并发恢复

三层互斥全部属于阶段 A，不能把第三层延后到开放续跑时：

1. 任务级：同一任务/已确认执行只允许一个有效执行体；领取使用预期 revision 和稳定请求身份。
2. 目标级：按规范化的稳定文件身份串行写入；多文件按稳定顺序取锁，覆盖读取写前态、预检、保存和必要核对，不能只锁最后 replace。Windows 大小写、路径别名及受支持的文件身份映射必须统一；无法证明别名一致性时保守拒绝。
3. 恢复级：核对后恢复文件、撤销和原执行使用相同的目标锁。只有确认原执行者不能继续写，才允许恢复；备份清理/导出仍须遵守现有生命周期占用保护。

阶段 A 可采用单机调度器和进程内锁，不要求分布式租约。但必须先约束并验证共享同一任务资料的服务单实例运行；若允许开发/安装服务或多 worker 并存，则必须加入跨进程排他，不能以仅监听 localhost 当作单实例证明。

保存领取修订或执行尝试令牌；过期执行者不能提交新 checkpoint 或开始下一次发布。心跳和 PID 只供诊断，过期不证明线程或进程已停止。超时释放逻辑锁但底层线程继续写入的实现不合格。

软暂停只有在没有在途写入、状态已持久保存时才能释放目标锁；继续时重新取锁并验证来源和写后态，不把锁跨越用户长时间等待。多文件部分发布待决状态需保留持久冲突标记，阻止 Excel Bro 的其他任务写这些目标，直到核对并解决或用户明确保留现状放弃恢复；它不能阻止外部 Excel 人工修改。

软件内部互斥不代替占用检查、写前条件和写后验证。Office.js 旧宿主仍可能写入且无法排除时，不允许自动接管未知写入；该安全约束不因后续阶段开放而取消。

## 8. 文件夹模式的具体设计

### 8.1 输入与中间工作簿

稳定输入可以是经授权保存的数据快照，也可以是重新打开后内容指纹一致的源文件。不能把当前文件与旧分页结果混合使用。版本建立在实际执行读取时，不把预览样本固定成写入值，也不宣称点击确认就原子冻结全部外部文件。

每个输入记录稳定身份、内容指纹、读取规则/工具版本和范围；结构指纹只证明字段兼容，不能证明数据值未变。多文件读取保存版本集合，并在获取前后复核或使用受控快照，保证没有在读取过程中混入修改。源既是输入又是输出时，保留原输入引用，发布后的文件不再充当原始输入。

保存中间状态时，checkpoint 必须引用所有受影响工作簿在同一逻辑时点的版本，不能只保存其中一个。保存的是可重新加载的文件或显式结构化结果，不序列化 openpyxl 内存对象。

若某段计算选择不保存中间工作簿，必须声明从哪个节点重算，以及它的输入和依赖；不能恢复时跳过尚未落盘的修改。

对于分组占比，保存游标时必须一并保存累计计数、分母状态和输入版本；分母尚未完整计算时，局部结果不能标为最终值。

### 8.2 发布边界

发布前冻结输出文件与工作表命名映射。恢复不得重新运行 rename 策略生成另一组名称。

复用已有恢复点，保存替换前副本、临时输出、预期写后指纹和应用状态。发布后重读验证。恢复时由单一恢复调度器依第 12 章核对实际文件，再修订任务记录；不是无条件把 manifest 的状态复制到任务记录。

多文件发布不是整体原子事务。首期串行发布，每文件保留记录；发生部分发布时先核对全部相关文件，再执行明确策略。不能一边回滚旧文件一边从后续节点继续。

按阶段明确策略：

| 阶段/选择 | 准入条件 | 行为 |
| --- | --- | --- |
| 阶段 A 核对/保留 | 任意遗留状态，资料先通过安全检查 | 只读核对，真实报告部分写入；不继续发布 |
| 阶段 A 恢复到执行前 | 原执行已停止、取得全部目标互斥、当前状态与恢复资料可核验，用户确认影响 | 已是写前态的文件不动，已是本次写后态的文件按记录恢复；未知项使自动恢复整体停止 |
| 阶段 B1 继续剩余发布 | 全部目标状态已确定、未发布目标仍是写前态、输入有效、输出完整、原确认有效，用户确认继续 | 已发布文件只补记/验证，按冻结映射发布剩余文件 |
| 阶段 B1 选择恢复 | 与阶段 A 恢复条件一致 | 持久登记 rollback 方向后只推进恢复流程，不执行后续原计划节点 |

恢复方案绑定 revision、目标集合和当前指纹，执行前再次核对。continue 与 rollback 是两个可选方向，不是逻辑矛盾；同一恢复操作只能选择一个。开始回滚后不得用旧继续请求恢复发布；回滚本身失败时进入恢复核对，不能借机切回原执行。若用户以后要重新运行，必须处理旧任务的写入状态并生成新的预览/确认。

恢复实现可复用现有指纹核对、救援副本及安全替换组件，但不能直接调用依赖内存 undo_stack 和 ready 的旧入口。新增独立恢复路径也要登记恢复意图和逐文件结果，覆盖“恢复一半再次退出”的场景。用户选择保留现状并放弃任务，不代表工作簿整体一致或验收通过。

### 8.3 恢复点触发与授权

- 只读节点及恢复查询可以保存任务元数据，不因此复制源工作簿或创建空备份目录。
- 同一次确认执行中，每个已有目标保留一份执行前副本；checkpoint 产物与恢复副本分类管理。
- 新建文件沿用 recoveryAction=remove 的恢复记录；撤销前确认未被后续编辑。
- 备份、源数据读取、产物生成及发布都必须在对应授权检查之后。
- 修改含未授权工作表的文件不能利用“整本重新保存”绕过现有规则。
- v1 是遗留 manifest，v2 是现行版本；两者均没有完整任务现场。导入时标为历史恢复记录，能力按证据提供，不伪造可续跑任务；v1 保持保守的历史读取/取出能力，不因导入获得直接恢复资格。

## 9. Office.js 当前工作簿模式

当前执行器在 Excel 宿主内运行。服务重启可以恢复服务器任务记录，但不能重建旧的 Excel.run 上下文。

本章既是阶段 C 的能力约束，也是当前受限实现的边界。已保存且可取得稳定 URL 身份的工作簿，可对 5 类区域动作登记写前快照、动作完成检查点和最终回执；未保存工作簿、来源与目标重叠、结构变化和复杂对象仍只按普通模式执行并明确说明不能跨重启自动续跑。

恢复必须重新连接同一工作簿，核对持久身份、工作表身份、目标范围和当前内容。仅凭文件名或工作表名不足以确定对象身份。对于未保存且无法跨重启可靠识别的工作簿，明确限制为不能自动续跑。

按动作声明恢复能力：

| 动作条件 | 阶段 C 开放条件/策略 |
| --- | --- |
| 只读查询，输入仍相同 | 可以重新读取或复用有效结果 |
| 可完整核对前后状态的确定性写入 | 有独立动作适配和测试后开放续跑 |
| 创建/删除表、排序、插入行等结构变化 | 先建立对象身份与完整效果核对，不按名称或节点序号直接重试 |
| 图表、透视表及复杂对象缺少可靠核对 | 保留恢复资料，明确暂停自动续跑 |
| 宿主不可用、工作簿已切换或未知写入仍可能进行 | 等待原工作簿重新连接，不转由文件夹后端接管 |

写入前的恢复资料和执行意图需要可靠登记；后端不可用且无法登记时，新恢复模式应停止继续产生未经登记的写入。前端本地日志可用于诊断，不升级为跨进程权威记录。

对只获得部分恢复覆盖的动作，UI 必须说明覆盖限制。恢复已有备份与继续后续节点是不同操作，不合并成一个含糊的“恢复”按钮。

## 10. 上下文、备用模型和预算

### 10.1 上下文恢复

保存用户最终确认需求、澄清的 append/replace 结果、messages、已完整接收的模型响应、工具调用与返回配对、结构化工作记录和摘要版本。

已确认的字段映射、分母、范围、输出目标独立保存，不能仅靠摘要或新模型重新猜测。摘要标明覆盖到的消息位置和依据，不把未完成响应归入已完成事实。

调用工具前先登记完整请求。若同一响应有多个工具调用，记录各自状态，恢复时只处理未完成调用。工具返回值存受控产物，用户可见事件只提供安全摘要。

缓存键包含工具及版本、规范化参数、来源版本和授权摘要；不能因“名称和参数相同”复用另一份文件的数据。

### 10.2 模型切换

- 仅在完整模型调用边界切换；中断的半份 JSON 或半条工具调用不得执行。
- 已完整保存的模型响应优先继续处理，不能因换模型重新生成同一批待执行工具。
- 备用连接必须由用户配置并允许用于任务；仅存在连接不代表可以自动向该供应商发送任务数据。
- 接续前核对工具调用、结构化输出、图像输入和上下文长度等实际能力，保持当前工具限制和规划阶段。
- 不兼容的供应商消息格式由适配层转换；不能直接透传不成对的 tool_call/tool_result。
- 当前完整 Key 通过后端配置引用获取，不复制到 checkpoint。
- 切换记录包含原因、旧/新连接身份和发生节点，界面显示简短说明。
- 用户已确认的写入计划不随模型切换改变。新模型改变语义或目标时产生新计划版本并重新预览确认。

当前实现只在规划任务因模型错误暂停后显示切换入口。用户必须显式选择一个已配置连接并确认；服务端保存旧/新连接身份与切换原因，继续沿用原消息、工具结果、授权、累计时间和 token/轮次预算。半份响应不会交给新模型，也不会自动尝试另一供应商。供应商消息格式或工具能力不兼容时继续保持暂停。

模型 HTTP 超时可能已在供应商侧产生费用。本地可以防止收到响应后重复执行工具，不能保证供应商只收费一次。调用返回 usage 不确定时记录未知项，不能把未知费用伪装为零。

### 10.3 预算连续性

保留 LoopState 中已有的累计 token、轮次、连续错误、工具路径和警告状态，同时保存修复模式、当前开放工具集合等影响下一轮行为的状态。

恢复和换模型不清零预算。有效运行时间与等待用户、停机时间分开；新增任务总期限可另行配置。重试预算需覆盖模型客户端内部重试和节点级重试，避免层层嵌套放大。

达到预算上限时维持停止状态，用户明确调整预算或创建后续任务后才能继续，不通过换模型绕过循环保护。

### 10.4 耗时提醒、累计活跃总时限与显式接续

以下行为已在 `/api/turn/stream` 的受支持规划路径实现。

**2026-10-10 改造：提醒与预算暂停已分离。** 此前 `planningReminderSeconds`（60 秒）
被当成"到期即暂停"的硬预算，真实多步任务每 60 秒就被打断一次、要求用户点击
"继续"。现在：

- `planningReminderSeconds`（60 秒，可配置）只是**非阻塞的耗时提醒**：超过它只发一条
  **限频**进度事件（`planning.reminder.<n>`），任务**保持运行**，界面不显示"继续"按钮；
  提醒不重置任何已完成步骤，也不伪造进度百分比。
- 真正的停止阈值是 `planningHardWallTimeSeconds`（1800 秒），按**累计活跃执行时间**
  计算。到达后由循环在"启动下一次模型/工具调用之前"收口
  （`note_progress(..., enforce_total_wall_time=True)`，它复用该边界**唯一一次**
  `save_boundary`），抛 `AgentBudgetPause` 并发出 `planning.budget_exhausted` 事件。
- 每个可恢复边界仍然照常落**检查点**（`save_boundary`）—— "取消短时暂停"**没有**
  连带取消检查点、错误恢复或中断恢复。**同一个边界只落一次**：总时限收口与耗时提醒
  共用同一次保存，`before_model` 不会出现两条检查点。

| 限制 | 职责 | 到达后的动作 |
| --- | --- | --- |
| 耗时提醒份额 | 让用户知道本轮跑得比预期久 | 发一条限频进度事件；**任务继续**，不显示继续按钮 |
| 累计活跃执行总时限 | 限制单轮总的有效运行时间 | 停止启动新的模型/工具调用，保存现场并如实说明；不承诺"必然可以继续" |
| 请求网络超时 | 防止单次连接无限等待 | 标记调用异常，按共享预算有限重试，不自行追加任务时间 |
| 任务预算（token/轮次） | 限制消耗与尝试次数 | 停止新工作；普通"继续"不能越过硬上限 |
| 连续错误/无进展保护 | 阻止反复提交同一错误或重复读取 | 说明原因并挂起，不能用延长时间清零保护状态 |

有效运行时间包含模型等待、内部重试退避、本地计算、保存和核对；**排队、等待用户和
服务停机不计入**。累计值跨重启沿用（写在检查点的 `loopState.activeElapsedSeconds`），
不因重连、点击继续或重试而归零。

暂停原因**必须分开呈报**，不得统一包装成"进度已安全保存"：

| `pauseType` | 含义 | 恢复能力 |
| --- | --- | --- |
| `budget` | 本轮预算暂停（未达总时限） | 可从这里接续现场继续 |
| `budget_exhausted` | 累计活跃执行时间已达总时限 | 不再启动新调用；如实说明，**不**显示必然可继续 |
| `model_error` | 模型连接中断且可换连接 | 按切换能力提供换模型接续 |
| `interrupted` | 服务重启等中断 | 检查点与引用有效才允许恢复 |

到达总时限后的处理顺序：

1. 循环在启动下一次模型/工具调用前判定；已达总时限则不再开始新的调用。
2. 在途请求与容器按既有可取消机制收口（`execute_python_analysis_async` 的
   `cancel_check` 接真实执行终止）。
3. 保存一致现场、最后已完成节点与暂停原因，抛 `AgentBudgetPause` 交上层登记。
4. 发出 `planning.budget_exhausted` 事件，如实说明"已用完，不再启动新调用"。
5. 界面按 `pauseType` 分别显示；`budget_exhausted` 不得显示成"必然可以继续"。

一条 `continue` 请求绑定 `taskId`、`expectedRevision`、稳定 `requestId`。重复点击或
断线重试**幂等**（同 `turnId` + 同 `requestId` 视为同一次），同一任务不能并发续跑；
旧 revision 不继续执行。续跑前重新验证授权、来源指纹、工作簿身份与引用有效性。

**旧短时预算暂停任务**：不自动恢复、不批量改动账本。用户点击一次"继续"即进入新
策略 —— 批准预算一次结清到总时限，累计耗时保留，随后按上述流程重新校验现场；
引用（`dataset://` / `result://`）已失效时明确要求重新读取或新建任务。

普通"继续处理"不隐式提高 token/轮次上限；硬上限之外不自动继续。文件临界操作不得
为守住精确秒数而强杀。

已有写入确认只在原计划版本、范围和输入约束仍有效时复用。**预算确认不是 Excel 写入
确认**；尚未确认的计划仍停在预览。

### 10.5 配置与最小现场要求

预算配置集中于 `config/capabilities.json`：

- `planningReminderSeconds=60` —— **非阻塞耗时提醒**阈值（不触发暂停）。
- `planningHardWallTimeSeconds=1800` —— 单轮累计活跃执行总时限（真正的停止阈值）。
- `planningExtensionSeconds` / `planningMaxExtensions` —— 预算追加的粒度与次数上限；
  新策略下初批预算即总时限，追加通常为 0，字段保留以兼容账本与历史记录。

生产规划循环的时间硬上限读取 `planningHardWallTimeSeconds`；旧 `agent.maxWallTimeSeconds`
保留为兼容配置但不再驱动该循环。轮次、token、连续错误和模型网络重试仍使用原有独立
限制，普通继续不会提高它们。

Claude Agent SDK 后端以 `planningHardWallTimeSeconds` 作单次请求上限，**没有** 60 秒
停顿，与普通后端在"总时限内自主执行"上语义一致。**SDK 后端没有检查点恢复能力**，
跨后端续跑由 `ModelNotAvailableError` 挡住（这是当前接入的限制，不代表 SDK 永远不支持）。

B2 当前保存原请求（含最终确认需求与来源指纹）、messages、LoopState、开放工具模式、工具缓存、修复状态、下一轮位置、完整待处理模型响应、事件序列、预算和稳定继续 requestId。刷新/重启后先查询持久状态，再按 revision 显式继续；已完成的模型响应和工具结果不会重做。半份响应不会成为 checkpoint，不具备这些证据的路径不展示续跑能力。

## 11. 授权、来源版本与确认有效性

授权来自服务端登记的任务范围；恢复请求只提交 taskId 和受控选择，不接收任意磁盘路径、脚本或替换后的 checkpoint。

重建文件夹 session 时按已登记根目录和既有范围核对。缓存不能恢复已撤销的授权，当前选区也不能静默替换任务范围。需要重新授权时明确列出缺少项。

来源比对区分：

- 外部输入：与任务采用的数据版本及语义条件比较。
- 本任务已经修改的目标：与最近已提交步骤的预期状态比较。
- 不确定写入：先进入第 7 章的核对流程。

中途来源变化时，默认使受影响计算结果及下游依赖失效；需要重新规划或确认的写入先停止。不能把原计划允许“执行时读取最新数据”直接推广成混用中断前后的数据。若要支持恢复时整体重算最新输入，必须作为明确策略并重新给出影响预览。

| 恢复时的输入/产物情况 | 规则 |
| --- | --- |
| 输入版本匹配、产物完整、工具兼容、授权有效 | 可以复用相应节点，不重读新版本混入旧结果 |
| 输入变化且尚未发布 | 失效受影响节点及其下游；如改用新数据，说明重算并按输出影响重新预览确认 |
| 输入变化且已经部分发布 | 先核对所有已有写入并解决旧发布方向；不得边保留旧输出边用新输入续算剩余文件 |
| 输入证据缺失，或仅有结构/mtime 证据 | 不足以证明数据一致，挂起或选择明确的重新开始流程 |
| 输入保持，但中间产物缺失/工具版本不兼容 | 仅从证据完整、无未处理副作用的较早节点重算；不满足则挂起 |

依赖失效必须记录起点、原因、受影响节点和保留节点。原始输入、任务自己的中间版本和已发布目标分别建引用，避免把本任务合法修改当作外部改动，也避免把人工改动当作自己的结果。每类可恢复工具应提交此表对应的具体版本定义和测试，不由模型临时解释。

原计划、范围、目标及输入约束仍有效时，用户点“继续”即可，不再逐步重复确认。扩权、改口径、改目标、覆盖影响变化时重新预览确认。

## 12. 存储、一致性、清理与迁移

### 12.1 建议布局与目录发现

任务元数据存本机应用数据目录，文件夹大型产物与既有恢复资料放在用户已登记的工作目录。阶段 A 已由 `server/app/app_data.py` 与 `packaging/runtime.py` 统一开发/安装解析规则：`EXCEL_BRO_CONFIG_DIR` 优先，否则使用平台应用数据目录，不依赖当前 shell 所在目录定位历史任务。

以下为逻辑布局。阶段 A/B 共用 SQLite，当前账本物理位置为 `tasks/state.sqlite3`：

```text
%LOCALAPPDATA%/Excel Bro/tasks/
├── state.sqlite3           任务身份、规划现场、事件、结果、预算、幂等墓碑及目录索引
└── artifacts/              保留给阶段 C 的受控大型规划/工具产物（B2 现场当前在 SQLite）

已登记的工作目录/.excel-bro-backups/
├── tasks/<sha256(taskId)>/ B1 已实现：文件夹任务的暂存工作簿与中间产物
├── executions/<undoId>/    复用：执行前副本与恢复清单
├── operations/             复用：恢复事务救援资料
├── exports/                复用：用户取出的副本
└── .trash/                 复用：事务清理暂存
```

目录按需创建，不移动用户源文件，不按节点把副本散落到桌面或源文件旁。无备份的目录不因查看恢复列表而创建空备份文件夹。若选择 SQLite，数据库仅放本机，不跟随工作目录放到共享盘。

数据产物按模式选定唯一受管位置；不在两处重复保存同一工作簿。当前工作簿模式不为了存检查点而默认建立新的工作目录。

阶段 A 已沿用用户设置工作目录的体验并增加后端持久目录索引。只索引服务端已安全校验并登记的目录；启动时只读取本机索引及其中允许检查的受管元数据，不扫描整盘、不自动读取原始数据行、不执行恢复。用户移除登记后停止自动扫描；旧任务仍保留“需要重新选择目录”的状态。

旧资料不在索引时，用户重新选择原工作目录后才导入；路径缓存、manifest 内路径、历史工作表勾选和短期令牌不能单独重建写入授权。目录缺失/移动/离线、权限改变、路径成为符号链接/junction/reparse point 时停止访问，要求重新确认映射；不能按同名文件自动寻找替代品。

扫描不能只检查 applying：覆盖 preparing、prepared、applying、recovering、needs_attention 及与任务完成状态不一致的记录，并检查中断的恢复事务。ready 只表示保存生命周期，不代表最终验收完成。旧 manifest 可导入为关联到目录的历史恢复事件，不补造完整 plan/messages 或自动获得 resume 能力。新任务从起始登记，不等到备份目录生成才拥有任务身份。

### 12.2 单一权威与跨记录核对协议

单一权威指“只有任务恢复调度器能批准下一次写入”，不是“只相信一个 completed 标志”。TaskLedger 保存调度决定；备份 manifest 保存文件恢复证据；实际文件决定效果核对是否成立。旧撤销接口和兼容执行入口也必须经过同一准入服务，不能各自根据 manifest 独立放行。

写入顺序固定为：领取任务和目标互斥 → 核对授权/原确认 → 提交含稳定 operation/execution/目标和预期效果的意图 → 持久准备备份及输出 → 登记 applying → 替换文件 → 核对文件 → 更新 manifest 回执 → 提交任务 checkpoint/预算/事件。任一步失败都不调度下一个业务节点，先处理该窗口。

恢复时先读取任务身份/版本/确认记录，再读取关联 manifest、产物和恢复意图，最后在持有目标互斥期间重新读取实际文件。路径、指纹或记录身份不可靠时停止，不把一份记录自动覆盖成另一份。

| 不一致情形 | 调度器的唯一处理 |
| --- | --- |
| 任务未完成，manifest/文件均匹配本次写后态 | 补记对应回执，再提交 checkpoint；不重放发布 |
| manifest 也未完成，但文件匹配事先保存的本次预期输出 | 核对身份、范围和恢复资料后修复回执；预期输出证据不足则挂起 |
| 任务/manifest 宣称完成，但文件仍为写前态、缺失或发生变化 | 否决直接续跑，登记异常并阻止下游；不能仅因看起来是写前态就自动再写 |
| 只有意图，文件仍为已核验写前态且没有其他副作用 | 阶段 A 只报告；阶段 B 经确认可重试支持的节点 |
| 部分目标是写后态，其余是写前态 | 持久记录逐目标结果，按第 8.2 节选择单一恢复方向 |
| 有 manifest 但没有完整任务身份/授权关联 | 导入历史恢复事件，只给与证据匹配的核对/取出/恢复入口，不伪造续跑 |
| 关键记录或产物损坏、文件两态都不匹配 | 保留现场，挂起并提供安全处理出口 |

补记/修复本身使用稳定 recoveryOperationId 和 revision，必须可重入；再次退出后重复核对，不跳过。文件发布或恢复未核对完成前，不发出代表业务成功的事件。

### 12.3 存储选型与提交契约

阶段 A 已通过 [ADR 0001](decisions/0001-task-ledger-and-folder-write-exclusion.md) 选择 Python 标准库 SQLite，使用 WAL、`synchronous=FULL`、busy timeout、唯一键和显式事务保存任务身份、事件、结果及受管目录索引。SQLite 是任务调度记录的权威，但不宣称包含外部 Excel 文件事务；恢复仍必须同时核对 manifest 和实际文件指纹。

无论选哪种载体，必须满足：

- 节点状态、checkpoint、预算增量和可重放完成事件作为一个原子提交单元；前端发送失败只重发，不再执行。
- 若用 JSON，需明确同目录临时文件、刷新/替换和受锁的预期 revision 比较；不能分别覆盖几个文件并称为一次事务。事件可与提交封装一起保存，再派生可查询视图。
- 若用 SQLite，需明确事务、同步配置、迁移及损坏策略；数据库事务仍不包含外部 Excel 文件替换。
- 产物先完成保存和校验，权威记录再引用；丢失或损坏的引用必须使节点不可复用。
- 跨 task 的目标互斥、备份占用和目录索引一致性不能依赖存储格式自动解决；派生索引可重建，不能独立批准写入。

保留 schemaVersion、executorVersion、toolVersion 与 checkpoint generation。升级需要显式迁移和兼容检查；未知版本保留资料、停止续跑，不能直接套用新版动作语义。

### 12.4 清理和隐私

- 活跃、挂起、结果未知及待恢复任务引用的产物均受保护。
- 暂存文件和执行前副本分别统计，不因快速撤销栈淘汰就删除续跑资料。
- 完成任务的大产物可按策略清理，但保留必要幂等标记；清理后的任务不能显示仍可完整续跑。
- 未被已提交 checkpoint 引用的孤立产物，确认无活跃写入后才能清理。
- 删除任务记录不等于撤销 Excel 操作。用户选择放弃任务时说明已有写入和保留的恢复资料。
- 清理复用安全目录检查、Windows reparse point 防护和可恢复事务删除；扫描器排除新受管目录。
- 新增任务恢复与存储限额统一放在 capabilities；不能仅沿用一小时的进度 TTL。
- checkpoint 可能含用户消息和数据，保存在受控本地目录，纳入容量与保留策略。
- 诊断导出仅含关联 ID、错误类别和状态；不得附带原始行、完整 Key 或完整上下文。
- 使用显式版本化数据格式，不通过 pickle 或任意代码对象反序列化恢复现场。
- 损坏记录、未经核验的目录和用户提供的产物路径不能成为扩大文件访问的依据。

首期重点验收进程异常退出和重启。断电耐久性还需核对文件刷新与系统行为，不能把“重命名成功”一概描述为断电后绝对可靠。

## 13. API、前端与用户体验

以下包含已实现的阶段 A/B/C 受限接口语义和后续拟议接口；状态以表中说明为准：

| 语义 | 状态 | 输入 | 行为 |
| --- | --- | --- | --- |
| 查询受管恢复目录 | 阶段 A 已实现 | 本机登记目录索引 | 只列出后端已登记且允许核对的目录及恢复摘要 |
| 查询文件夹执行 | 阶段 A 已实现 | operationId | 返回运行、完成、失败或需核对状态；查询不会创建执行 |
| 订阅文件夹事件 | 阶段 A 已实现 | operationId、afterSequence | 补发已提交事件并复用终态结果 |
| 独立恢复文件 | 阶段 A 已实现 | directoryId、undoId、expectedRevision、稳定 operationId、明确确认 | 取得与原执行相同的目录排他，核对后续修改与 manifest 后恢复到执行前；重复请求可重入 |
| 查询规划任务 | 阶段 B2 已实现 | `GET /api/turn/{turnId}/status` | 返回持久状态、revision、事件位置、预算、来源指纹及是否可继续；查询不会自动继续 |
| 文件夹续跑预检 | 阶段 B1 限定实现 | operationId、持久 checkpoint | 仅对单个 `splitGroupAggregate` 核对授权、产物、manifest 和各文件真实指纹 |
| 继续文件夹发布 | 阶段 B1 限定实现 | operationId、expectedRevision、明确确认 | `POST /api/folders/execute/resume/stream` 原子领取后只发布未完成文件；不重新计算 |
| 追加预算并继续 | 阶段 B2 限定实现 | turnId、expectedRevision、稳定 requestId、明确确认 | `POST /api/turn/continue/stream` 检查硬上限，同 requestId 只追加一次；不授权 Excel 写入 |
| 通用节点续跑 | 阶段 C 未实现 | taskId、恢复方案修订 | 尚不支持任意动作、任意 DAG 或子任务栈继续 |
| 取消/放弃 | 后续扩展未实现 | taskId、预期 revision | 记录停止意图，安全结束；不隐式删除已经写入的结果 |
| 切换接续模型 | 阶段 C 限定实现 | turnId、允许的 connectionId、expectedRevision、明确确认 | 只在完整模型调用边界切换到已配置连接；保留消息、工具结果、授权和全部累计预算 |
| 登记/查询 Office 写入现场 | 阶段 C 限定实现 | operationId、已确认计划、授权表、稳定工作簿 URL 身份 | 写入前持久登记；状态查询不返回写入令牌，也不创建新任务 |
| Office 动作回执 | 阶段 C 限定实现 | operationId、revision、短期 ownerToken、动作序号、写前快照或写后检查点 | 只支持 5 类可核对区域动作；每一步写前登记、写后提交，旧 revision 或令牌拒绝推进 |
| Office 在途核对并续跑 | 阶段 C 限定实现 | operationId、真实目标范围、明确用户操作 | 重新连接同一工作簿；匹配预期结果才补记，匹配写前状态才重试，其他状态保持挂起 |

恢复预检和真正执行之间仍需复核，不能依赖预检时刻的旧状态。未知任务 ID、已过期状态和不匹配内容应明确报错，不创建新任务。

旧文件夹执行接口逐步转接持久任务执行器；兼容入口不能绕过持久幂等登记。前端不得在可能已经开始执行后回退到另一条无幂等的新写入请求。

界面建议在相关对话保留一张任务卡：

预算暂停样例（数据由真实现场生成，不写死进度或剩余时长）：

> 任务已暂停，等待你确认是否继续。  
> 本段已处理约 60 秒；字段核对和数据读取已完成，还需生成并校验方案。  
> 继续将追加界面所示的处理预算；不会因此直接写入 Excel。  
> 操作：继续处理（注明追加额度）、稍后继续、停止任务。

如果尚在完成安全收尾，改为“正在安全暂停”；保存失败则明确说明，不能展示“已保存”。“稍后继续”保持等待，“停止任务”记录取消并说明已有写入，不等于撤销。没有可靠工时估计时只描述剩余步骤，不承诺再等多少秒一定完成。

模型连接中断样例（仅在对应接续能力已交付后展示）：

> 任务已暂停：模型连接中断。已保存数据读取结果。  
> 可以从“生成分析计划”继续，无需重新读取。  
> 操作：继续任务、选择备用模型、放弃任务。

结果未知时显示不同提示：

> 上次保存可能已修改文件，正在核对实际结果。核对完成前不会重复写入。

后台仍运行时显示“重新连接进度”，不要显示“重新执行”。完成、挂起和恢复期间沿用同一时间线身份；使用恢复分段或标记说明接续，避免重复卡片和错误的步骤完成数。

刷新后先查询真实状态，再恢复界面。暂停卡应说明可复用步骤、需要重算部分、已发生写入、需要用户处理的条件；不把 checkpoint、lease 等实现词汇直接放入普通操作引导。

## 16. 验收与故障注入矩阵

所有工作簿测试使用隔离副本。故障注入须包含真实子进程退出与重新启动，不能只抛出可被 except 捕获的异常。

| 编号 | 注入场景 | 验收结果 |
| --- | --- | --- |
| C01 | 前端流连接断开、后台继续执行 | 同 taskId 补收结果，执行次数不增加 |
| C02 | 任务窗格刷新 | 查询并挂接原任务，无新的写入请求 |
| C03 | 工具结果完成后结束服务 | 恢复复用完整结果，不重复调用已完成工具 |
| C04 | 一批工具只完成其中一部分 | 只处理剩余调用，messages 与结果配对合法 |
| C05 | 内存动作完成但未保存中间工作簿 | 从有效计算边界重算，不错误跳过 |
| C06 | 产物落盘后、checkpoint 事务前退出 | 未提交产物不冒充完成，可校验收用或安全重算 |
| C07 | 原子任务记录/checkpoint 提交后、事件发送前退出 | 补发已提交事件，不重跑节点 |
| C08 | 文件已替换、完成回执前退出 | 核对写后指纹后补记，不重复发布 |
| C09 | 多文件仅一部分发布 | A 仅核对/受控恢复；B1 按确认方向继续或恢复，方向互斥，真实报告部分结果 |

| C15 | 多窗口连点继续；旧执行者失联但线程仍活着 | 至多一个有效写入者；无实际排他权不接管，旧领取者不能继续提交或并发写 |
| C16 | 操作记录过期、清理或服务重启后重放旧请求 | 返回既有结果/取消/过期状态，不重新创建执行 |
| C17 | 模型超时并切换允许的备用连接 | 保留语义、完整结果及预算，不重复工具副作用 |
| C18 | 备用模型不支持工具/图像或未获发送授权 | 不静默降级执行，明确等待合适连接 |
| C19 | 达到累计预算后恢复或换模型 | 不清零，不绕过停止条件 |
| C20 | checkpoint 提交失败、空间不足或产物损坏 | 不跳过关键结果；已写入部分仍可核对与恢复 |
| C21 | 暂存/备份清理与恢复同时发生 | 活跃引用和异常资料保留，无悬空 checkpoint |
| C22 | 同名输出使用 rename，随后重启 | 使用原先冻结名称，不新增另一套输出 |
| C23 | 用户在保存临界区取消 | 记录取消意图并核对实际结果，不虚报未写入 |
| C24 | Office.js sync 后、持久回执前宿主退出 | 有完整证据才补记；否则挂起，不盲目重放 |
| C25 | 未保存工作簿、同名不同文件或复杂对象无法核对 | 明确不支持自动接续，不操作错误宿主 |
| C26 | 升级后读取旧 checkpoint 或旧备份 manifest | 兼容迁移或保留待处理，不伪造可续跑状态 |
| C27 | 只读任务创建检查点 | 无 Excel 写入、无源文件副本、无空备份目录 |
| C28 | 诊断导出、上下文恢复与模型切换 | 不泄露 Key，不将完整恢复资料作为普通日志发送 |
| C29 | 处理到软阈值，当前节点已安全完成 | 保存现场后等待确认，不继续新业务节点；显示真实已完成/剩余内容 |
| C30 | 阈值到达时模型响应仍在途，随后完整返回 | 保存完整响应/待调用列表；若任务直接完成则不多余暂停；半份 JSON 不执行 |
| C31 | 软阈值或硬预算到达时正在文件替换 | 先安全收尾和核对，不强杀写入线程、不提前释放锁，不趁收尾推进额外业务 |
| C32 | 重复点击追加预算、响应丢失重试、旧 revision 请求 | 同 requestId 仅追加一次，旧修订拒绝，不出现双执行或额度翻倍 |
| C33 | 预算等待期间刷新/重启/关闭页面 | 找回同一暂停任务；不自动同意，不重新计时清零；显式停止不被启动扫描复活 |
| C34 | 时间与 token/轮次同时耗尽 | 时间追加不隐式提高其他额度；错误历史保留；超硬上限仍拒绝普通继续 |
| C35 | 预算暂停期间输入、授权或计划发生变化 | 重新核对，旧结果按依赖失效；需要新预览的写入不能靠预算确认放行 |
| C36 | 开发/安装切换，已登记目录移动、离线或成为 reparse point | 定位规则一致；失效路径只提示重新选择，不整盘搜同名文件，不自动恢复权限 |
| C37 | 原执行、独立恢复、撤销、兼容入口指向同一文件 | 统一准入和目标锁；不同 operationId 也不能并发写；备份占用保护仍有效 |
| C38 | 恢复到执行前只完成部分文件，进程再次退出 | 按独立恢复意图核对并接续恢复方向，不重新发布原计划，不覆盖后续编辑 |
| C39 | 任务/manifest 已完成但实际文件缺失或仍是写前态 | 否决直接续跑，挂起核对；记录不凌驾于文件证据 |
| C40 | 同进程 operation 被 TTL/容量淘汰但 session 仍有效，再重放旧执行 | 明确既有结果/过期/需核对，不进入创建分支再次写入；与 GET 状态行为分别测试 |
| C41 | 连续同类错误或无新进展，用户反复延时 | 无进展保护仍生效，解释原因；不能通过追加预算清空错误计数 |
| C42 | 模型超时、节点重试与退避叠加，且用户等待很久 | 共用硬预算，等待用户不计运行时间；未知调用费用不计零，不层层放大重试 |
| C43 | 多服务实例、同文件路径大小写/别名访问 | 验证单实例约束或跨进程排他；不同拼写不绕过目标互斥 |

分阶段验收范围：A 必测持久身份/事件与未知写入（C01–C02、C07–C08、C11、C14–C16、C20–C21、C23、C26–C28、C36–C40、C43），并覆盖 C09 的核对/恢复分支；其中依赖节点或模型接续的分支先验收准确拒绝。B1 增加 C05–C06、C09 的继续分支、C10、C12–C13、C22；B2 增加支持路径的 C03–C04、C19、C29–C35、C41–C42。C1/C2 增加 C03–C04 的逐工具场景、C17–C19；C3 增加 C24–C25 的实际接续能力。自动化已覆盖核心状态机，C3 仍必须在真实 Excel 中注入“sync 后、回执前退出”和同名不同文件场景。

结果对比应读取实际工作簿，核对数据、公式、类型、结构与支持的属性；不能只比较进度条或文件存在。Excel ZIP 容器时间戳等可能影响字节比较，业务等价性与发布文件身份指纹分别验收。

性能需要测量检查点增加的耗时、内存与磁盘峰值、恢复耗时和可复用比例。大文件不能因每步全量序列化而耗尽空间；先基于固定数据集确定粒度与上限。

## 17. 需要评审重点回答的问题

1. 写入已经发生但回执未保存时，每一类动作是否都有足够证据判断结果？哪些动作必须降级为人工核对？
2. 文件夹计算的检查点粒度是否合理？完整工作簿、结构化结果和可重算区间如何取舍？
3. 第 12 章单一权威与核对协议是否完整？所选存储如何实现原子提交，能否避免记录冲突导致重复发布？
4. 哪种工作簿身份能跨刷新/重启可靠成立？Office.js 未保存文件应限制到什么范围？
5. 失联后，如何保证旧执行者不再写入？是否覆盖进程内线程、跨进程和路径别名，以及恢复与原执行的竞争？
6. 原授权、执行确认与恢复确认的有效性是否足够明确？是否会过度询问或绕过原确认？
7. 模型客户端和调度器如何共享重试预算？未知供应商调用用量如何记录？
8. 多文件部分发布时，阶段 A 的核对/恢复与阶段 B1 的继续规则是否可实现，并与现有撤销链一致？
9. 哪些资料必须长期保留，哪些可以清理？幂等标记删除后如何拒绝旧请求？
10. 数据来源或工具版本变化，如何确定失效依赖和允许重算的最早安全位置？
11. C01–C43 是否覆盖关键失败窗口，是否还缺任务记录/文件双失败、升级中断等阻塞场景？
12. A/B/C 的交付范围是否准确？是否会把阶段 A 说成已能续跑，或把 B2 所需的最小现场错误推迟到 C？
13. 软阈值、硬上限、追加份额/次数和无进展判断如何定值？是否能通过普通继续绕过 token/轮次或写入确认？
14. 预算暂停期间刷新、重启或修改来源后，继续入口是否准确恢复原任务而非重新发起需求？
15. 工作目录索引的登记、移除、失效路径与授权重建是否明确，能否避免文件到处存放或自动扩权？

请把“建议完善”与“阻止安全实现”区分开。若提出引入新框架，应说明它具体解决哪项问题，以及仍需自行实现的 Excel 效果核对、授权和文件事务部分。
