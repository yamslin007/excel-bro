# Agent 任务上下文与本地澄清整合（2026-10-08）

## 本批落地

之前的 SDK 已接入，但每次 `query` 独立，字段意图、规划和前端补全之间没有同一份显式业务确认。本批不复制 CLI 会话，也不另建任务账本：在已有任务记录上投影有界 `taskContext`，两种模型后端、Excel/WPS 两端共用其语义。

`taskContext` 只包含 `schemaVersion=1`、原始用户需求、用户明确提交的确认项（questionId / label / value）。同一道题后答替换先答；正常新任务从空确认开始；显式替换需求同时更新请求和恢复记录，旧规则不再进入后续追问。Excel 先保存已提交的上下文再发意图请求，断线后可在原卡重试/改答；WPS 继续沿用现有 TaskResumeRecord 保存真实答案。恢复操作不是写入许可。

协议同步 `apps/excel-addin/src/contracts.ts` 与 `server/app/models.py`，共享类型与构造器在 `packages/core/src/agentTaskContext.ts`；限额集中在 `config/capabilities.json` 的 `taskContext`。服务端严格拒绝未知键、错误类型和超长项。前端白名单重建，不将本地映射源值、规则草稿、目标矩阵、授权对象或模型转录作为确认项。

普通意图、普通 Agent 主循环、SDK 意图和 SDK 规划都消费同一份结构化确认及同源指导：保留已确认决定，只问真正缺项。提示词并非模型行为的绝对保证；本地源值覆盖、授权与写入仍由确定性工具独立检查。

## 本地补全卡

Excel/WPS 使用同一组件和确定性补全逻辑。完整、有限、无歧义的 `valueRank` 沿用，不根据 p0/p1 等标签含义或映射声明顺序猜业务高低。新增目标等级、缺失/冲突等级或人工调整排序时仍需确认；只有已有一个目标等级时无需选择相互高低。

空值、公式、重复映射就地显示具体输入问题，并在提交前禁用按钮，勾选排序不再使空字段通过。整格精确映射优先、最早声明分隔符的缺项检测与执行器保持一致。补全后重新读取授权源列，再在本机生成白名单计划；不会自动写回。已知目标的新来源项可以沿用已有顺序；新目标的位置不能自动推断。

## 保持的边界与未实现项

- SDK 仍通过项目 MCP 白名单工具提交受控终局，未开放 Read/Bash/Edit、宿主脚本或任意命令。
- SDK 仍使用独立 `query` 和 `--no-session-persistence`；本批实现的是显式业务上下文续接，不是 SDK 原生会话或精确检查点恢复。跨后端检查点仍显式拒绝。
- SDK 仍拒绝 `planningReadPolicy != none` 或非空 dataResults。原始源值、原始历史/结果和私有路径不会因 taskContext 接入而被新增到 SDK 请求。
- 此上下文不是数据授权或写入确认。当前授权变更、源值改变、预览失效仍需原有守卫处理；所有宿主写入仍经过 AnalysisPlan、预览及独立用户确认。
- 普通 Excel 文件夹模式使用相同协议；本批不新增 WPS 文件夹入口，也不开放隔离 Python 产品入口。没有改三点提示样式。

## 如何试用

1. 后端协议已变，先停止旧后端，再按现有方式启动。SDK 通道仍使用 `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start_claude_sdk_server.ps1`，不同时启动第二套后端。
2. 刷新/重新加载 Excel 和 WPS 任务窗格。无需删历史、变更模型密钥或扩大数据授权。
3. 在独立测试簿选择数据范围，发送映射需求，明确多项优先级和空值策略。补充两轮后检查预览是否保留两条规则；只有真实未覆盖值才在本地卡补全。
4. 用已声明完整等级的规则补一个“来源项→已有目标”，应沿用优先级；引入新目标应要求确认位置。空目标/公式应立即指明具体字段且不能提交。
5. 测试改答同一道题、替换需求后继续追问、网络失败后重试，以及新对话中发起不同任务。核对旧规则不会串入，源列仍重读，未确认时原表零写入。

真实 Excel/WPS、真实 SDK 模型行为仍需按以上清单验证；不能仅以单端测试或同款 UI 宣称所有能力已对齐。
