# 工作日志 2026-08-22

## 主题：计划从「烘焙快照」转向「可编辑活脚本」

### 用户反馈的问题

> 工具不太万能，改了一个单元格后就没办法正常执行，而且没地方编辑脚本。

三个症状，一个根因。

### 根因

**计划是一次性的结果快照，不是可复用的程序。**

链路是这样的：前端 `dataTools.ts` 确定性算好数据 → 作为 `dataResults` 塞进
`PlanRequest` → 服务端拼进 prompt 并砍掉三个只读工具逼模型直接用现成结果 →
模型把 rows 当**静态值**塞进 `writeValues.values`。

由此派生：

1. **改一格就拒绝执行** —— 值指纹闸对来源表逐格哈希 value+formula+numberFormat，
   任意一格变化 → 整份计划一步不执行。这道闸本身是**合理的**，因为计划里的值确实
   过期了；它是「烘焙」的症状，不是病本身。
2. **没地方编辑** —— 计划预览只有人话步骤列表；固化工具的 DSL 视图是**有损**只读
   （矩阵渲染成 `<MATRIX ROWS=x COLUMNS=y>`），无反向解析器；`storage.ts` 无
   `updateTool`。
3. **不万能** —— 白名单动作 + Excel 公式表达力覆盖不了多步中间状态、不规则脏数据
   解析、循环递归、动态输出形状。

### 已有的正确范式

`splitGroupAggregate` 是原先唯一的活计算动作，它的三点形状就是本次要复制的模板：

- action 只带配置不带结果
- 执行端读实时 `sourceRange.values` 调纯函数现算
- 验收条件跳过 `RangeEquals`，只加 warning

有利前提：`dataTools.ts` 的算子（filters / groupBy / metrics / ratio / profile /
sortAndLimit）**全是纯函数，不依赖 Office.js** —— 「读」绑 Excel，「算」是纯的。
把「算」从生成时挪到执行时，技术上只需在执行阶段调这些现成纯函数。

### P2 抽出 `readSheetIntoAccumulator`

`dataTools.ts` 的分块读表 + 表头识别循环抽成可在外部 Excel context 复用的导出函数。

这段逻辑有个微妙点：首块用 `detectHeaderIndex` 识别表头，后续块**手动把 header 拼

错，且只在跨块（>5000 行）时暴露 —— 所以要求 `dataTools.test.ts` 零改动全绿，另补

### P3 `ComputeValuesAction` 模型与验收条件

复用 `QueryTableArguments`（已含 filters/groupBy/metrics/sortBy/limit/mode）而非重造。
它原本定义在 `ExcelAction` 联合之后，上移到联合之前（Pydantic 前向引用对顺序敏感）。

**验收条件是这一步的爆破点**：`add_deterministic_acceptance_criteria` 对
`computeValues` 只补 `WorksheetExistsCriterion`，**永不补 `RangeEquals`**。原因是
`RangeEqualsCriterion` 有硬校验 —— range 尺寸必须等于 expected 尺寸；执行时求值下
行数未知，连 range 都填不出，Pydantic 会直接抛错，且错误信息指向验证器不指向根因。
用回归测试锁住了「computeValues 只产出 worksheetExists」，模型定义处也留了显式注释。

### P5 指纹闸分级

原先一道闸卡所有情况，现在按计划 liveness 分三档。新增公共地基：

```ts
const BAKED_ACTION_TYPES = new Set(["writeValues", "writeTable"]);
export function planLiveness(plan) {
  return plan.actions.some((a) => BAKED_ACTION_TYPES.has(a.type)) ? "mixed" : "live";
}
```

`writeFormulas` 归 live（公式引用单元格，Excel 自己重算）。`filterRange.values`、
`setDataValidation.values` 是用户点名的配置取值而非算出的结果，也归 live。

| 情况 | 用哪种指纹 | 变化时行为 |
|---|---|---|
| 固化工具（基线本身是 schema 指纹） | schema 指纹比对 | 不一致 → 拒绝 |
| `live`（全执行时求值） | 直接体检表/字段在不在 | 仍在 → **放行**；缺失 → 拒绝并报出缺了什么 |
| `mixed`（含烘焙矩阵） | 值指纹 | 抛 `StaleSourceError` → UI 二次确认，不再直接堵死 |

**为什么 live 档不复用 schema 指纹比对**：指纹只能拿「计划生成时存下的那串哈希」当
基线，而 live 计划存的往往是值指纹（旧规则），没有 schema 基线可比。拿现算的哈希跟
自己比是恒等式，什么都挡不住。所以新增 `missingSchemaRequirements()` 逐项查在不在，
并把缺了什么直接报出来。

（这个恒等式缺陷是第一版实现里真实存在的 bug：live 无条件放行、mixed 走到通用
`PlanExecutionError` 就返回了，`StaleSourceError` 和它的确认按钮全是死代码。已修。）

mixed 档文案：`数据来源在预览后发生了变化，这份计划里有 N 处写入的是预览时算出的
固定值，执行会写入旧结果。建议重新生成预览；也可以坚持执行。`

preflight 不受影响 —— 它完全不读单元格值，结构保护不削弱。

### P6 可编辑 JSON

直接暴露 `AnalysisPlan`，不做 DSL 双向解析、不做结构化表单。

- 新增 `components/PlanJsonEditor.tsx`：`.tool-drawer` 抽屉 + 普通 `<textarea>`。
  故意不引入 Monaco / CodeMirror —— 会把包体积翻倍，而这里编辑的是几十行 JSON，
  收益撑不起成本。
- 新增 `hooks/usePlanEditor.ts` 承载编辑态、校验、指纹重算、回写，让 `App.tsx`
  只留接线。用 `PlanEditorTarget` 区分「消息里的计划」和「固化工具的模板」，一个
  hook 实例服务两个入口。
- 两个入口：计划预览 `<details className="plan-details">` 内的「编辑脚本」，以及
  固化工具专家视图里的「编辑脚本（JSON）」。后者的徽章从「只读展示」改成
  「可编辑 JSON」—— 加了编辑按钮之后原文案就成了假话。

**校验双阶段**：

1. 前端 `JSON.parse` + `assertEditablePlan`（从 `assertAssistantResponse` 的 plan
   分支抽出导出）—— 手改的计划和模型生成的走**同一道白名单门**，否则「能编辑」就
   变成了绕过白名单的后门。
2. 服务端 `POST /api/plans/validate` 跑 Pydantic 规范化，**返回规范化后的 plan**。

**保存路径强制走服务端规范化，绝不允许前端自己拼 `acceptanceCriteria`。** 编辑后有
四个可变量（plan 内容、liveness、指纹前缀、验收条件），任意两个不同步 → 「保存成功
但执行时验证失败」，这种沉默错比不能编辑更糟。

`assertEditablePlan` 只做结构与白名单校验，不查 title/summary 之类必填字段 ——
那些交给服务端 Pydantic，前端多加一层只会和既有调用方打架（第一版加了，直接打红
3 个 contracts 测试）。

新增 `storage.ts:updateToolPlanTemplate(toolId, plan)`：参数是从 `planTemplate`
反推的（哪个动作的哪个属性该暴露成工作表/字段选项），换了计划就必须重算参数 ——
否则运行工具时会拿旧参数去绑不存在的动作下标。审批项同理，编辑后可能新引入了固定
内容或破坏性动作。

指纹重算加了守卫：只有原本就是 schema 指纹的计划才重算，值指纹要读实时单元格，
不在这里做。

### P7 Web Worker 纯计算沙箱（代码已完成，等 P0 实测放行）

四个文件按依赖顺序写完：`protocol.ts`（消息协议 + `validateSandboxOutput`）→
`computeWorker.ts`（Worker 本体）→ `runComputeScript.ts`（主线程 runner，硬超时）
→ `sandboxSafety.ts`（静态黑名单），加上服务端 `ComputeScriptAction`。

**隔离靠环境，不靠黑名单。** `computeWorker.ts` 不 import 任何模块，Worker 全局里
本来就没有 Office.js、没有 DOM、没有 fetch —— 脚本写了 `fetch(...)` 只会得到
ReferenceError。`sandboxSafety.ts` 的黑名单是服务端前置过滤和可解释信号（告诉用户
「这段脚本试图联网」比运行时 ReferenceError 好懂），不是主防线。这个定位写进了文件
头注释，避免后来者误以为放宽黑名单就等于放开沙箱。

黑名单分两组，取舍不对称：网络/IO 组（fetch / importScripts / Office / Excel /
localStorage 等）**硬拒绝不接受配置放宽** —— 命中说明意图就不对；反射组
（eval / Function / `.constructor` / `__proto__` / globalThis）会误伤合法写法，
由 `sandbox.allowReflection` 控制。测试里显式传参而非依赖配置当前值，否则改一次
配置就会让用例含义整个翻转。

**硬超时是这条线唯一真防线**：AbortSignal 中断不了正在死循环的 Worker，Worker 也
没法给自己设闹钟，只能主线程 `setTimeout` → `terminate()`。这正是 P0 必须实测
`terminate()` 有效的原因。一个 Worker 只服务一次调用，不复用 —— 省几毫秒启动开销
不值得上一段脚本的全局状态污染下一段。

`validateSandboxOutput` **刻意不做隐式转换**：undefined / Date / 嵌套数组一律报错，
不悄悄修正。沙箱输出直接落进用户工作表，静默转换会把「脚本算错了」伪装成「数据看
起来怪怪的」，比直接报错难查得多。唯一例外是 NaN / Infinity —— Excel 承载不了，
必须挡在写入前。Worker 侧和主线程侧各校验一遍：前者为快速定位，后者才是写入前的
安全兜底。

补齐的接线（这些漏一个就会静默失效）：

- `format.ts` 动作文案 —— 漏了会让 `actionLabel` 缺 return 分支（tsc 直接报错）
- `excel.ts` preflight —— 源表存在性、单单元格目标、静态黑名单前置
- `excel.ts` `verificationGaps` —— 与 `computeValues` 同样只认 dynamicCriteria
- `excel.ts` `requiredToolFieldsBySheet` —— 脚本引用的列名写在脚本里无法静态提取，
  只登记源表本身，让 `missingSchemaRequirements` 至少能查表是否还存在
- `folder_workbooks.py` unsupported 集合 —— 文件夹模式没有 Excel 端 Worker 通路

**`toolDsl.ts` 护栏 footer 改成按计划内容如实标注。** 含 `computeScript` 时输出
`ARBITRARY_CODE = SANDBOXED_PURE_COMPUTE`，否则仍是 `DISABLED`。这份 DSL 是用户会
读的护栏声明，计划里确实有脚本要跑却还印 DISABLED 就是在说假话。其余护栏
（VBA / EXTERNAL_PROGRAM / MODEL_REINTERPRETATION）不受影响，测试把这点钉住了。

**沙箱默认关闭**（`sandbox.enabled = false`），因为 P0 还没实测。服务端
`ComputeScriptAction` 的验证器会在开关关闭时直接拒绝，所以协议一致性测试用
monkeypatch 临时打开而**没有改 config** —— 改配置会让默认部署悄悄启用沙箱。

### submit_plan schema 预算闸（第二次撞上）

`computeScript` 作为第 38 个动作进入联合体后，schema 从 26035 涨到 26680，顶破了
26000 的闸。这次和 P8 性质不同：**不是描述啰嗦，是真实内容增长**（动作本体 645
字符 + 判别映射 48），加之前只剩约 13 字符余量。

选择**在 `_strip_metadata` 里一并剥离 `default`**（26680 → 25247，余量 753），而不是
抬上限。理由是 `default` 描述的是服务端在字段缺失时的行为，**不是模型必须满足的
条件** —— 剥掉它模型能生成的合法计划集合一个都没少，`maxLength` / `minLength` /
`enum` / `anyOf` 这些真约束全部保留。测试加了断言把这条界线钉住：真约束必须在，
`default` 必须不在。

界线是「削注解可以，削约束不行」—— 后者会让模型看不见真实边界从而反复提交非法
计划。可剥的注解到此见底，测试注释里写明了：**下次顶破时诚实的做法是抬上限**，
不是去削 maxLength。

未验证的一点：模型看不到 `default` 会不会变得冗余地把每个字段都写满。原理上不该
（不知道默认值照样能省略字段），但服从度只有真实对话能验。
