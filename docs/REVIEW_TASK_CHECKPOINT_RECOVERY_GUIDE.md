## 1. 总体结论

**需要调整方向。** 不建议按 R0–R5 全套实施。

被评审文档的概念纪律质量很高，罕见地守住了几条容易被含糊掉的边界：不把"有备份"说成"能续跑"、进度事件不作为节点成功证据、退回 checkpoint 不撤销已落盘写入、"同名表存在"不构成动作已完成的证据。第 4.4 章崩溃窗口表和第 7.3 章效果核对表是本文档最有价值的部分，即使不实施整套方案也应保留。

但它缺了决定整套方案价值的一节分析：**重算的成本是多少。** 583 行中一次都没有出现这个问题。checkpoint 的收益等于"省下的重算成本"，而本项目的目标任务规模决定了这个收益在规划阶段接近于零、在文件夹阶段又恰好被已选定的架构方向抵消（见 2.1、2.2）。

同时，方案把若干"全新基建"写成了"沿用现有能力"，会让实施成本被系统性低估（见第 4 章事实错误）。

## 2. 阻塞级问题

按严重程度排列。每项含触发条件、后果、证据、建议与验收方法。

### 2.1 【阻塞】R2 的目标阶段整体只有 60 秒，接续设计的收益无法覆盖成本

**触发条件**：实施第 10 章（上下文恢复、备用模型接续、预算连续性）与 R2 阶段。

**后果**：为一个墙上时间上限 60 秒、且无外部副作用的纯只读循环，建立持久化现场、跨进程预算连续性、供应商能力协商与 fallback 调度。收益上限是省掉最多 60 秒的只读重跑；成本是第 5 章中 Context / ToolReceipt / Budget 三类记录加供应商消息适配层，以及 C17–C19 三条故障注入用例。

**证据**：`config/capabilities.json`

| 键 | 值 |
| --- | --- |
| `agent.maxTurns` | 8 |
| `agent.maxWallTimeSeconds` | 60.0 |
| `agent.maxTotalTokens` | 20000 |
| `llm.timeoutSeconds` | 60.0 |

规划阶段被限制在 8 轮、60 秒、2 万 token 以内。`server/app/turn_state.py` 的 `TurnRegistry` 已提供内存幂等缓存（TTL 3600 秒、`maxActive` 500），已完成回答/计划在同一进程内不会重复生成。

**建议修改**：R2 整段移除。规划阶段的正确定位是"失败即整轮重跑，成本可接受且已被 8 轮预算封顶"。若模型连接不稳定确实构成痛点，应作为独立的重试/切换议题处理，而不是绑在 checkpoint 方案里——它不需要跨进程状态。

**验收方法**：先测量真实数据。在现有 `agent_loop_protection` 上加计数，统计规划阶段实际耗时分布与失败重跑频次。只有当"重跑成本 × 发生频率"显著时，才重开此项。

### 2.2 【阻塞】与已定的"执行时求值"架构方向冲突，文档提出了矛盾但没有给出路

**触发条件**：实施 R3（文件夹写入接续）时，计划中包含执行时求值动作（`computeValues`、`splitGroupAggregate` 类运行时读数）。

**后果**：checkpoint 的本质是冻结某一时点的状态；执行时求值的本质是拒绝冻结。二者相遇时，恢复只能退化成全量重算——而全量重算的开销恰恰集中在文件夹模式（`folder.maxFiles` 100、`queryTable` 上限 25 万行 / 100 列 / 100 万单元格）。结果是：检查点机制在最需要它的场景下失效，R3 会实现一套用不上的中间产物存储。

**证据**：被评审文档 §11 自己写道"不能把原计划允许执行时读取最新数据直接推广成混用中断前后的数据"，并在 §8.1 要求"不能把当前文件与旧分页结果混合使用"。这两条都只是**禁止混用**，没有回答"那么恢复时读哪一版"。§11 末尾把"恢复时整体重算最新输入"列为"必须作为明确策略并重新给出影响预览"——即事实上退回全量重算 + 重新确认，此时 §8.1 的中间工作簿产物没有被复用。

**建议修改**：这是设计前提，必须先解决再谈实施。两条可选路径：

- **路径 A（推荐）**：承认执行时求值动作不提供中间产物续跑，只提供"识别中断 + 核对已发生写入 + 恢复到执行前"。检查点范围收缩到**发布边界**，不做计算中间态。
- **路径 B**：为执行时求值引入显式的"输入版本冻结"语义，让计划在确认执行的瞬间锁定数据版本。这与项目从烘焙快照转向活脚本的方向相反，需要单独论证。

**验收方法**：在 R0 退出条件中增加一条——对每一类执行时求值动作，写出"中断后读哪一版输入、依赖如何失效、是否需要重新预览"，无法回答的动作明确标注不支持续跑。

### 2.3 【阻塞】引入 SQLite 会造成两个权威来源，文档承认风险但把收口留给了实施者

**触发条件**：实施第 12.2 章，任务数据库与既有备份 manifest 并存。

**后果**：两套记录各自判断"是否可以再次写入"，在崩溃窗口内必然出现分歧。这是重复发布（数据损坏）的直接来源，风险高于方案要解决的原始问题。

**证据**：被评审文档 §12.2 自己指出"不能让两个来源各自独立决定可以再次写入"，随后以"提交边界不确定时以实际效果核对收敛"作结——这是把最高风险处交给了实施细节。§17 第 3 问同样把这条列为待回答问题，说明设计未完成。

同时，现有 manifest 的完备度被低估了：

| 现有能力 | 证据 |
| --- | --- |
| manifest 版本控制 | `folder_workbooks.py`：`BACKUP_MANIFEST_VERSION = 2`（约 214–215 行） |
| 完整生命周期状态 | `preparing` / `prepared` / `applying` / `ready` / `recovering` / `restored` / `rolled_back` / `needs_attention` |
| 前后内容指纹 | 备份前后均记录哈希，撤销前核对，拒绝覆盖后续人工编辑 |
| 恢复动作记录 | manifest.json 记录 `recoveryAction`（含新建文件的 `remove`） |
| 安全清理 | 先移入 `.trash` 再异步删除，Windows 占用重试 |
| 磁盘空间预检 | 写入前检查 64 MB 安全余量 |

也就是说，"记录已发生的写入意图与效果"这件事，manifest 已经做了；缺的只是**启动时的扫描与用户出口**。

**建议修改**：**不引入 SQLite。扩展 manifest 作为唯一权威来源。** 相应地，§7.4 的 lease / heartbeat / 执行世代整段移除——本项目是单机本机工具（FastAPI 仅监听 `127.0.0.1`，安装包自启动单个服务进程），不存在多执行者竞争。软件内部锁本来也拦不住用户在另一个 Excel 实例改文件（§7.4 末尾自己说了），保留占用检查 + 写前条件核对 + 写后验证即已足够。

**验收方法**：C16、C21、C26 三条用例改为只针对 manifest 单一来源验收。原 C08（文件已替换、完成回执前退出）应能仅凭 manifest 的写后指纹完成核对——若能，则数据库不必要，这本身就是判据。

### 2.4 【阻塞】§9 / R4 违反项目已确立的通道边界原则，且交付物多数为"不支持"

**触发条件**：实施 Office.js 当前工作簿模式的动作级恢复能力表。

**后果**：R4 的交付物是一张能力表，而按文档自己列出的限制，表中多数行是"不支持"：未保存工作簿不支持自动续跑、图表/透视表缺少可靠核对需暂停、结构变化（建删表/排序/插行）需先建立对象身份、宿主不可用时不得由后端接管、无法强制隔离旧执行者时不允许自动接管未知写入。为一张以"不支持"为主的表建立逐动作适配层和 C24–C25 验收，投入产出不成立。

**证据**：被评审文档 §9 的动作条件表；`apps/excel-addin/src/excel.ts`（约 4510 行）的 `executePlan` 为顺序执行 + 同步循环，无持久节点调度器；§9 自己承认服务重启无法重建 `Excel.run` 上下文。

**建议修改**：按"分流点往前挪、不要在两套语义之间架桥"的既定原则，**当前工作簿模式明确声明不提供跨进程续跑**，前端在检测到中断时只做一件事：告知上次执行可能未完成，引导用户使用现有会话内撤销资料或人工核对。删除 R4，删除 §9 的逐动作适配设计，保留 §9 中"仅凭文件名或工作表名不足以确定对象身份"这条判断作为通用纪律。

**验收方法**：C24、C25 降级为"界面正确显示不支持自动接续，且不操作错误宿主"。

## 3. 非阻塞但应修正的问题

### 3.1 第 1 章现状表偏乐观（前端重连）

文档写"部分网络异常最多自动重连一次；完整流结束却缺少结果等错误并非都会重试"。实际更严格：

`apps/excel-addin/src/api.ts` 的 `executeFolderPlan`（约 521–646 行）循环条件为 `attempt < 2`（即最多重连一次），但重连的前置条件是**错误不是 `ApiRequestError`**（约 625–635 行）。因此 **`retryable = true` 的 `ApiRequestError` 也不会被自动重试**。

**建议**：改为"仅对非 `ApiRequestError` 的网络类异常重连一次；`ApiRequestError` 即使标记 `retryable` 也不自动重试"。这条影响 C01 的验收口径。

### 3.2 第 1 章现状表的"重载后挂接"结论应从"未发现"升级为"确认没有"

已核对 `App.tsx` 与 `useActivityProgress.ts`，未见任何对执行状态接口的调用；`afterSequence` 补收只在同一会话生命周期内生效。这一条可以从推断改为已验证。

### 3.3 事件补收的丢失窗口未被描述

`_folder_request_fingerprint`（`main.py` 约 611–618 行）对 `FolderExecuteRequest` 除 `operationId` 与 `afterSequence` 外的全部字段做 SHA256（含 `sessionId` 与完整 plan）。`operationId` 由前端生成（`api.ts` 约 517–518 行，`folder-<时间戳36进制>-<随机>`）。补收使用 `min(request.afterSequence, len(state.events))`。

事件列表本身没有独立的缓冲上限，但 `_prune_folder_operations`（约 723–731 行）与容量淘汰（`folderMaxPendingOperations` 100，约 932–944 行）会整条移除 operation，**该任务的全部事件随之消失**。文档 §1 末尾提到了 TTL 与容量淘汰会移除已结束任务，但没有明确指出"淘汰即事件全丢，补收会返回空而非缺口报错"。

**建议**：在 §1 或 §13 补一句，并明确恢复接口在遇到"任务已被淘汰"时必须返回明确的过期状态，不得静默返回空事件列表（这一点 §7.2 有对应要求，但两处没有连起来）。

## 5. 推荐的最小实施范围

替代 R0–R5。核心判断：**把检查点范围收缩到发布边界，复用 manifest，不新增数据库。**

### 5.1 阻塞项（建议实施）

| 项 | 内容 | 依据 |
| --- | --- | --- |
| M1 | 服务启动时扫描 `.excel-bro-backups/executions/*/manifest.json`，识别处于 `applying` / `needs_attention` 的遗留记录 | manifest 已记录该状态，仅缺扫描 |
| M2 | 新增只读接口：列出当前工作目录下的遗留中断记录及其核对结论（依 §7.3 的证据分级） | 复用现有前后指纹 |
| M3 | 前端在相关对话展示一张卡片，给出三个明确出口：**核对实际结果 / 恢复到执行前 / 放弃并保留资料** | §13 的卡片文案可直接采用 |
| M4 | 三态分离表达：任务结束 / 写入成功 / 业务验收成功必须能分别显示（含"已写入，验证未通过"） | §6.1，纯收益，与是否实施 checkpoint 无关 |
| M5 | 前端重载后调用 M2 接口重新挂接，且**不得回退到无幂等的新写入请求** | 修正 3.2 的确认缺口 |

预计规模：数百行，无新增存储层，无新增协议对象类型（复用 manifest 结构 + capabilities 中的保留策略）。

### 5.2 应采纳的概念纪律（零成本，纯收益）

以下三条从被评审文档中提取，建议直接写入开发规范，与实施范围无关：

1. 进度事件是展示记录，**不单独作为节点执行成功的证据**（§2.2）。
2. "同名表存在"或"文件存在"**不构成动作已完成的证据**（§7.3）。
3. 取消请求发生在文件替换临界区时，**先记录取消意图，再完成该临界操作的核对或回滚**，不得直接报告"没有修改"（§6.3、C23）。

### 5.3 明确声明为不支持（写入文档而非实现）

- 进程崩溃后的自动续跑：不提供。理由是目标任务规模下重跑成本可接受（`agent.maxWallTimeSeconds` 60 秒；文件夹执行为秒级至分钟级）。
- 断电耐久性：不声明。当前无 fsync。
- 多文件部分发布后的自动继续：不提供，一律进入核对流程。
- Office.js 当前工作簿的跨进程续跑：不提供（见 2.4）。

### 5.4 后续扩展项（留待真实需求驱动）

- 中间产物续跑（依赖 2.2 的架构矛盾先解决）。
- 备用模型接续（依赖 2.1 的耗时测量结论）。
- fsync 与断电耐久性（需独立的平台行为核对与故障测试）。

## 6. 尚无法证明的保证

以下三项在现有代码基础上拿不出证据，**不应进入任何对外能力声明**：

1. **断电后的耐久性**。落盘路径为 `workbook.save(临时文件)` + `os.replace()`，无 fsync。文档 §12.3 末尾的免责声明是正确的，应上移到第 4 章。
2. **多文件部分发布后的自动继续**。§8.2 自己说明"多文件发布不是整体原子事务"且"不能一边回滚旧文件一边从后续节点继续"，但 §8.2 末尾仍建议"首期对所有目标状态确定的任务允许继续发布"。这两句在部分发布场景下相互冲突，C09 无法验收。
3. **Office.js 未知写入的自动接管**。§7.4 已明确"对无法强制隔离旧执行者的 Office.js 通道，首期不允许自动接管未知中的写入"，这一条应提升为硬约束而非首期限制。

## 7. 关于"建议完善"与"阻止安全实现"的区分

按被评审文档 §17 末尾的要求：

**阻止安全实现的**：2.3（双权威来源判断可否重写）、2.2（活脚本恢复时读哪一版输入未定）、第 4 章中 §4.2 对不存在的 fsync 能力的依赖。这三项若按当前文档实施，会产生重复发布或数据版本混用的真实风险。

**建议完善的**：2.1、2.4（成本收益不成立，但不产生正确性风险）、第 3 章全部、第 4 章其余事实错误。

**未提议引入新框架**。被评审文档 §3 与 §15 已正确指出框架迁移不是实施前提，此判断予以确认——Excel 效果核对、授权边界与文件事务这三块是本项目的实际难点，任何 Agent 框架都不提供。

## 8. 对 §17 待答问题的处理建议

§17 列出 12 个待回答问题，其中以下 4 个是**设计前提而非实现细节**，未回答即不具备实施条件：

| § 17 编号 | 问题 | 本评审对应章节 |
| --- | --- | --- |
| 1 | 写入已发生但回执未保存时，每类动作是否有足够证据判断结果 | 2.4、第 6 章第 3 项 |
| 3 | 任务数据库与既有 manifest 不一致时的核对修复顺序 | 2.3（建议：不产生第二个来源） |
