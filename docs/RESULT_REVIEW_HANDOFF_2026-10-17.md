## 一、修掉的真实问题

1. **WPS 自动执行通道被整段注释**（`TODO: resultReview 自动执行通道当前已禁用`）。
   它主张"跳过了写入前确认，违反先预览后确认"，与用户已授权的"先执行、后审阅"冲突。
   结果：面板退回旧的"先生成副本再写回"卡片，`ResultReviewBar` 永不出现。
2. **执行器从不返回恢复记录**（`confirmPendingPlan` 只在 `finally` 里收尾，**没有 return**）。
   审阅通道拿到 `undefined` 就判"执行未完成"，而表已经写了、恢复点也在 ——
   用户看到"执行未完成"，实际状态却是"已写入且可撤销"，最容易诱发重复执行。
   现在把记录提到 `try` 外并在成功路径登记、函数末尾返回。
3. **写回闸门把"我自己发起的执行"当成"忙"**。审阅通道先置 `pending=true` 再执行，
   闸门若把该 pending 也算忙，就会拦下自己发起的写入 —— 拦不拦得住取决于中间有没有
   恰好一次重渲染，表现为**时灵时不灵**（同一份代码有的用例能写、有的报"执行未完成"）。
   现在这条通道只认自己的在途锁 `writeBackInFlight`，界面忙态由发起点判定。
4. **可选双视图被做成了写入的前置条件**（两处）：
   - `prepare` 里直接 `stageWpsNativeComparison(..., true)`，即 `Worksheet.Copy()`；
     宿主没有复制接口时**连写入都被挡掉**。
   - 第一版修补把"格式快照采集"也放进 `prepare` 并要求完整 —— 同样会因可选功能拒绝写入。
   现在 `prepare` 只做内存快照（新增 `captureWpsBeforeResult`），格式采不到只记录、
   不阻断；真正打开双视图时才明确说"无法完整重建执行前格式"。
5. **双视图拿到的不是"执行前"状态**（本次最实质的缺陷）。执行在前，若再复制当前表，
   副本就是执行后的样子；而 `stageWpsNativeComparison` 还会拿预览快照比对已变的原表
   而直接抛错 —— 双视图根本打不开。新增 `stageWpsBeforeComparison`：复制后把
   **执行前快照**逐格写回副本（公式写公式、常量写值），格式动作按快照恢复；
   原表一格不动，也不采用"临时还原原表再复制"这种会短暂破坏现场的做法。
6. **执行后计划信息丢失**：执行一结束 `pendingPlan` 清空、计划卡消失，用户看不到
   采用了哪些口径、格式动作改什么、行高列宽"影响整行"。新增只读的「本次执行计划」
   摘要卡（假设/警告/格式说明/完整计划 JSON），不提供编辑。
7. **从结果卡撤销后，固定操作条不同步**：条上仍显示"请查看主表中的执行结果"并提供
   「确认变更」，而结果已被还原；「保存为工具」资格也可能仍然开着。新增
   `ResultReview.settleExternally(executionId)`（只同步状态、**不再次恢复**），两端
   撤销成功回调里接线；`discard()` 自己的恢复流程因 `pending` 在位不会重复处理副本。

8. **确认/放弃收尾后固定操作条不收起**（WPS 实机）。成功终态后那一大块只重复
   "已确认变更"，却一直占着输入框上方。根因是共享 `ResultReviewBar` 对终态没有出口：
   阶段进 `confirmed`/`discarded` 后照旧整块渲染。
   修法：`settled && !needsAttention` 时返回 `null`（`needsAttention` = 在途 / 标记待清 /
   有提示）。**收起 ≠ 抹掉结论** —— 结果卡、保存为工具、撤销入口各自仍在；
   "这件事已经定了"改由一条收尾消息承载（WPS 既有 `settledLoggedRef`，本轮给 Excel
   `App.tsx` 补上同一条，否则共享组件一改，Excel 端会连状态说明一起丢）。
   真正没做完的收尾（标记未清、副本未关）仍留一条紧凑提示 + 对应动作。
   **没有**通过清掉恢复点或销毁执行记录来"把条藏起来"。

9. **双视图把副本当成了新的授权目标**（WPS 实机，最实质的那个）。
   真机序列：原表 `ss.xlsx` → 点「双视图对比」→ WPS 把副本（工作簿1）激活成
   `ActiveWorkbook` → 确认/放弃报"工作簿或授权发生变化"，数据范围面板也开始读副本，
   并反复提示"检查期间目标发生变化，请刷新后重新选择"。
   四处根因，逐个修：
   - `resultReview` 的 `isCurrent()` 直接读 `ActiveWorkbook.FullName` ⇒ 改成
     `wpsReadWorkbook()`。
   - `authorizeWpsSheets` / `assertWpsAuthorization` / `listWpsWorksheets` /
     `probeWpsWriteCapabilities` / `inspectWpsRecoveryState` / `wpsPythonData` 也都读
     活动簿 ⇒ 统一改走 `wpsReadWorkbook()`。
   - 没有"本次审阅 = 原表 + 本次副本"的绑定 ⇒ 新增
     `apps/wps-addin/src/wpsResultReviewTarget.ts`（**替换**上一轮那份带全局 Proxy 的
     未完成草稿，不采用全局替身）。绑定记下原表身份、副本身份、写入表；识别副本只认
     **创建时记下的身份 + 未保存 + 单表 + 表名一致**，不用"工作簿1"/`EB_` 前缀/
     活动窗口/名字相似度。
   - `adopt` 在比较之前就 `setAuthorizationRevision(+1)` ⇒ 只在授权键真的变了才递增
     （版本号是"已提交范围的身份"，不是"用户点过确认"的计数）。

   边界仍然守住：切到**无关**工作簿、原表被关、授权变化、计划变化一律照旧拦下
   （`wpsReadWorkbook` 只在"活动簿就是本次副本、且原表可被证明仍在场"时才解析回原表；
   证不出来就返回活动簿）。**没有**无条件跳过 `targetGuard`，也**没有**把活动簿全局替换。

10. **数据范围面板被挤压/遮挡、层级混乱**（WPS 实机）。
   根因：面板是 `.composer` 的后代 + `position:absolute; bottom: calc(100% + 7px)`，
   于是要吃输入框那一层的 `z-index:5`、`backdrop-filter: blur(10px)` 与外壳
   `overflow:hidden` —— 审阅条一出现、窗口一矮就被挤扁/截掉，还和输入区叠。
   修法：面板本体改由 `scopeOverlay` 挂到外壳的**直接子层** `.scope-layer`
   （`position:absolute; inset: 8px 10px 10px; z-index:40`），触发器那一行仍留在
   `scopeDock`（输入框上方）。标题也从滚动容器里搬出来（放在里面它就是"内容第一行"，
   一滚就跟着走），只有中间列表滚。结果卡里的「撤销本次执行」补上 `secondary-button`
   （此前是浏览器默认样式）。

11. **审阅标记不醒目**（实机："绿色细边框像普通网格，用户看不到变更区域"）。
    根因：两端标记都只画绿色细边框（Excel `#2F7650` / WPS `0x50762F`），没有区域底色，
    在带网格线的表里几乎不可辨。
    修法（两端读同一份纯判据 `packages/core/src/reviewMarkStyle.ts`）：
    - **不修改填充的动作**（写值/公式/清空/字体/对齐/行高）→ 浅黄临时底色 `#FFF3B0` +
      醒目金黄边框 `#B8860B`（WPS 边框 `Weight=2` 加粗）。
    - **涉及填充变化的动作**（`setFill`）→ 只用边框，不叠底色，保证实际填充结果可见。
    - 底色写在**独立条件格式规则**自己的 `Interior`/`FormatFill` 上，不是单元格的
      `Interior`/`format.fill` —— 删规则即随标记一起消失，不覆盖业务填充、也不靠
      "存旧底色再还原"。确认只清本次标记；放弃真实恢复后清标记；用户自己的条件格式
      （及其顺序、语义）保留。
    - **执行前副本不带入本次标记**：WPS 的 `Worksheet.Copy()` 会把原表已打上的审阅规则
      带进副本，重建时按 `EB_REVIEW_` 前缀清掉副本里的本次规则（用户规则保留），
      避免"两边都高亮、误以为执行前也是这个颜色"。Excel 副本由执行前快照重建，
      本就无标记。
    - 界面图例同步：`ResultReviewBar` 的"彩色边框是审阅标记"改为
      "变更区域以浅黄色底色与醒目边框标出（改了填充的区域只画边框）"。

12. **副本清理用前缀匹配会误删另一轮审阅的标记**（用户点名的收紧扣）。
    原来 `clearReviewMarksFromCopySheet` 按 `Formula1.startsWith('=N("EB_REVIEW_')`
    判定归属：另一轮审阅/另一个任务的标记**同前缀但 nonce 不同**，会被一起清掉。
    现在收紧到**本次实际创建标记的完整随机公式**（`markWpsResult` 生成的
    `marks.formula`，经面板 `mark` → `showBefore` 传给
    `stageWpsBeforeComparison` 的第三参 `reviewFormula`）：对不上完整公式的一律不碰。
    没拿到本次公式时**不清理**（宁可副本多一圈高亮，也不误删别人的规则）。

13. **标记策略只看单个动作，会漏掉"区域重叠"导致的遮色**（用户点名的第二个收紧扣）。
    原来 `reviewMarkStyleForAction(action)` 只看**这一个**动作是不是 `setFill`：
    - `setFont` 与 `setFill` 落在同一区域时，`setFont` 那块被判成 `fill+border`
      ⇒ 浅黄底色会盖住 `setFill` 刚写进去的真实填充；
    - 写值区域与 `setFill` 区域**部分重叠**时，写值那块同样被判成 `fill+border`
      ⇒ 重叠部分的填充结果被底色盖住。
    现在改为 `reviewMarkStyleForPlan(actions)`：按**整份计划的区域重叠关系**算每块
    区域的样式 —— 一块区域只要与**任何** `setFill` 动作的区域（同一工作表内）
    **矩形相交**，就 `border-only`；区域解析不出时**保守** `border-only`
    （证明不了不被 setFill 碰到，就不叠底色）。与动作先后顺序无关。
    两端读同一个函数（Excel 直接传 `plan.actions`，WPS 把 `sheetName` 映射成 `sheet`）。

14. **悬浮「回到底部」浮标把"等人"当"在跑"**（WPS/Excel 两端同症）。
    两端都传 `<ScrollToLatestButton running={busy} />`，而 `busy` 含
    `resultReviewState.phase === 'reviewing'` —— 那是"结果已就绪、等用户确认/放弃"的
    **交互锁定**，不是运行。于是执行早结束了，浮标还在跳三点。
    修法：**不删 `reviewing` 条件**（它承担防重复执行与操作互斥），而是新派生一个
    `running`：`busy` 原样保留，`running = busy` 减去 `phase === 'reviewing'`
    （Excel：`status !== 'idle' || nativeComparison.pending || resultReviewState.pending`；
    WPS：`baseBusy || resultReviewState.pending`）。
    这样：模型请求 / 执行 / 回读 / 生成对比 / 确认收尾 / 恢复在途 ⇒ 三点；
    只是等人查看、确认或放弃 ⇒ 已有的主题色锚图标。

## 二、最终用户流程（当前代码行为）

1. 提交要求 → 白名单 `AnalysisPlan` → 本地校验（授权范围、计划合法性、来源快照）。
2. 校验通过即**在授权范围内执行到主表**；执行期操作条只有"正在执行"。
3. 执行完成 → 主表显示结果 + 本次变更区域打临时审阅标记；固定操作条出现
   「双视图对比 / 放弃变更 / 确认变更」（常驻滚动区外）。
4. 「双视图对比」：仅在此时按执行前快照建立副本；打开/关闭/重复点击都不再执行计划；
   建立失败只提示，不影响已执行结果与撤销。
5. 「确认变更」：复核实际结果 → 只移除**本次**标记 → 开放"保存为工具"与"撤销本次执行"，
   不重放计划，也不等于保存磁盘文件。
6. 「放弃变更」：走真实恢复点撤销（有冲突/部分失败则不声称已恢复），成功后处理本次副本。
7. 从结果卡撤销：操作条同步转入终态，确认入口撤下。

## 三·十、悬浮浮标：运行状态 ≠ 交互锁定（两端同步）

| 要求 | 落地判据 |
|---|---|
| `busy` 原样保留（防重复执行/互斥不松） | 两端 `busy` 定义一字未改，仍含 `phase === 'reviewing'`；面板里 `if (busy) return`、`disabled={busy}` 等互斥闸全部照旧 |
| 新派生 `running`（实际在途） | Excel：`status !== 'idle' \|\| nativeComparison.pending \|\| resultReviewState.pending`；WPS：`baseBusy \|\| resultReviewState.pending`（`baseBusy` = 进度/写入进度/目标核对） |
| 模型请求/执行/回读/生成对比/确认收尾/恢复在途 ⇒ 三点 | `resultReviewState.pending` 覆盖审阅通道每个操作（`resultReview.ts` 的 `finally { pending:false }`）；`status`/`nativeComparison.pending`/`baseBusy` 覆盖其余 |
| 仅等人查看/确认/放弃 ⇒ 锚 | `phase === 'reviewing'` 且 `pending === false` 时 `running` 为 false |
| 两端同口径、不只测共享按钮 | 两端各一条**调用层**回归：`WpsAgentPanel.test.tsx`「review bar is waiting for the user…」、`excelWriteEndToEnd.test.tsx`「waiting for the user is not running…」 |
| 反向变异（接线判别力） | 把 `running={running}` 改回 `running={busy}`：WPS 用例红在「只是等用户查看结果时，浮标应当显示锚而不是三点」，Excel 用例红在 `expected 'running' to be 'idle'`；改回即绿 |

**调用层回归怎么证明"不是替身画锚"**：三条断言绑在**真实状态**上，而不是绑在按钮输入上 ——
① 审阅条的 `aria-busy` 与 phase 文案（证明此刻 `pending=false`、`phase=reviewing`）；
② 把恢复流程的 `targetGuard.check()`（→ `inspectOfficeAuthorizedTarget` /
`inspectWpsAuthorizedTarget`）挂住，同一条用例里接着断言 `aria-busy="true"`、
按钮 `disabled`，并等到浮标变成三点；③ 释放后等它回锚。
`busy` 的边界也在同一用例里复核：恢复入口在非 pending 时可点、恢复成功、固定条收起。

## 三·五、审阅标记生命周期（本轮补齐）

| 要求 | 实现与判据 |
|---|---|
| 确认只移除本次标记，不重放计划、不覆盖原有格式 | Excel 用**独立条件格式规则**（只画边框），WPS 用独立 `FormatCondition`；删除时按规则 id（Excel）/随机 `Formula1`（WPS）逐条核对，对不上就拒绝删除。`resultReview.test.ts`「只写一次」+ 两个标记模块用例。 |
| 清理失败保留可重试状态，重试只清标记 | `ResultReview.retryMarkerCleanup()`：不重新校验结果、不 `accepted`、不写表、不撤销。状态位 `markerPending` 决定界面是否出现「重试清理标记」。 |
| 刷新/重载后识别遗留标记，持久记录只含归属 | 两端新增 `excel-bro.reviewMarks.v1` / `excel-bro.wps.reviewMarks.v1`：只有表名、区域、规则 id（Excel）、随机公式。**不含任何单元格值/公式**。面板挂载时调用 `recover*ResultMarks()`。 |
| 创建部分成功后失败仍可追踪 | 每创建一条就落盘一次；失败先尝试清理，清理也失败则**保留**记录并如实说明（不留无主标记）。 |
| `settleExternally` 四处状态一致 | 阶段→`discarded`、清标记、`markerPending=false`、副本收尾；保存工具资格由两端撤销回调同步作废（既有逻辑）。 |
| 撤销成功但标记清理失败要分开说 | `discard()` 改为**先恢复、后清标记**；标记失败只写次要提示「主表已恢复到执行前；审阅标记未能全部移除…」。 |
| 归属不确定不得按颜色/区域/前缀批量删 | 只按记录里的规则 id / 随机公式删除；身份不符时**什么都不做**并保留记录。R5 变异把这条打回"按区域全删"会立刻变红。 |

**已知限制（如实记录）**：若 localStorage 里的归属记录本身丢失（清缓存/换机器），那些
残留规则就**无法被安全认领** —— 我们不会退化成"按区域清空规则"，因此只能由用户手动删除。
这是刻意选择：宁可留一圈边框，也不误删别人的格式。

## 三·六、执行前副本的完整性边界（WPS 侧实际行为）

`prepare` 只做**内存快照**（`captureWpsBeforeResult`：值、公式、格式动作的逐格格式、
行高），不建副本；用户点「双视图对比」时才 `stageWpsBeforeComparison`：复制当前表 →
把快照逐格写回副本 → 原表一格不动（不做"临时还原原表再复制"）。

| 属性 | 来源 | 说明 |
|---|---|---|
| 单元格值与公式 | **快照重建** | 复制到的是执行后状态，逐格写回（公式写公式、常量写值） |
| 字体/填充/边框/对齐/换行/数字格式 | 原生复制 + **快照恢复（仅本次格式动作范围）** | 动作范围内的格式按执行前快照恢复；范围外沿用复制值（本就是当前=执行前，除非执行前被人改过） |
| 行高 | **快照恢复** | 格式快照逐行采集 `rowHeight` 并按行恢复 |
| 列宽 | **不作为**：计划层已拒绝 `resizeRange.columnWidth` | 列宽未量化验证；`stageWpsBeforeComparison` 另有一道防御，含列宽即拒绝打开对比 |
| 条件格式 / 批注 / 合并 | **原生复制保留** | 本产品的写入动作不修改它们，所以副本与执行前一致；不重建、也不声称"已验证" |
| 公式重算结果 | 副本内重新计算 | 不宣称"历史计算值逐格一致"：只保证结构与公式文本来自执行前快照 |

无法证明完整性时（格式未采到 / 含列宽动作 / 宿主无复制接口）：**拒绝打开本次对比**并说明
原因，主表结果、确认与撤销一律不受影响。

## 四、17 条 WPS 失败的处置方式（逐类）

不是"都算旧测试"：每类都保留了原来的业务判别点，只换交互入口与取证时机。

- **入口迁移**（副本按钮/确认写回 → 固定操作条的「双视图对比/确认变更/放弃变更」）：
  `stageAndSave` 助手改为等待结果条；写回失败、格式闭环、连续链路等用例照此迁移。
- **取证时机迁移**（"等待审阅阶段本就有写入"）：原"零写入"断言移到**计划到达之前**
  （桥接收据前后、本地补全前）；计划到达之后改为断言"只写一次/只写目标表"。
- **替身不真实**（真实缺陷被替身掩盖）：
  - 本地计划替身只记账不改值 → 回读必然不符；改为真正按坐标写值。
  - 缺 CAP-03 账本端点 → 登记失败导致写入被安全中止；补齐 register/action/complete，
    并回显 descriptor（真实服务端会校验它）。
  - 桥接用例在服务端已判 `source_changed`/`unauthorized_scope` 后仍放出一份计划 →
    改为放行普通回答（真实服务端不会再下发计划）。
  - 双视图替身缺 `stageWpsBeforeComparison` → 补上，并把"建副本"断言改到新入口。
- **业务性质保留**：本地计划不出站/不落盘、源值变化零写入、工具复用按当前授权校验、
  连续 Python 链路真实写回与撤销，均仍在断言里。
- **仅两处按授权删除**：`marks the preview as edited`（编辑计划已取消）与
  "在途期间点放弃"（执行不再由点击发起，该界面路径不存在），均在原位写明原因，
  对应的守卫改由纯函数判据与"执行期间无按钮"覆盖。

## 六、最短双端实机验收步骤

1. 各准备一本**独立测试工作簿**（含一张已授权表、非空目标区域）。
2. 提交一条明确写入要求 → 主表被写入、变更区域出现标记、固定操作条出现三个按钮，
   且**没有**"确认写回"这一步。
3. 点「双视图对比」→ 副本显示**执行前**的值/公式/格式；反复开关、重复点击，
   主表不变、也没有第二份被改过的副本。
4. 点「确认变更」→ 标记消失，"保存为工具"与"撤销本次执行"可用；点撤销 → 主表回到执行前。
5. 重跑同一要求，点「放弃变更」→ 主表恢复；若副本已打开，只关闭该副本，
   原表窗口不动、不弹原表保存提示。
6. 执行前手动改动目标区域一格，再执行 → 应拒绝并说明来源已变化、零写入。
7. 执行后先用结果卡「撤销本次执行」，再看固定操作条 → 应已转入终态，不再出现「确认变更」。

**刷新加载项后要补看的四步（本轮三个问题的验收点）**

8. 执行 → 点「双视图对比」（WPS 会把副本激活）→ 直接点「确认变更」：
   应成功，不再报"工作簿或授权发生变化"；标记清零、固定条收起、撤销入口仍在。
9. 同上但点「放弃变更」：原表恢复，只清理本次副本，原表窗口不动、不弹原表保存提示。
10. 副本获得焦点时打开数据范围面板：显示的是**原表**与它的授权工作表，
    不再反复提示"检查期间目标发生变化，请刷新后重新选择"。
11. 数据范围面板在 300px / 430px / 宽窗格与矮窗口下各看一次：
    标题与底部「确认/取消」始终可见，列表自己滚，不与审阅条/输入框叠。
